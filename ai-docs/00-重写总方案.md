# 0. 结论摘要

**现工程是什么**：一个**纯前端、单机、无服务端**的放置/RPG 网页游戏。React 17 + MobX 6 + Immutable.js + react-router 6 + webpack 5，全 JavaScript，legacy 装饰器。约 **6,460 行核心逻辑**、**4,327 行页面**、**183 个数据文件**。游戏状态全部在浏览器内存中，靠 `localStorage` 持久化，用 JWT/自定义编码做**混淆式**防篡改（密钥硬编码在前端）。

**重写的本质**：不是"换个 UI 框架"，而是**把游戏状态的所有权从浏览器搬到服务器**。现工程的全部逻辑（战斗、掉落、成长、生产、剧情）都是**乐观执行 + 本地存档**；重写后要变成**服务端权威 + 客户端只负责表现**。

**四个必须提前想清楚的结论**：

| # | 结论 | 依据 |
|---|---|---|
| 1 | **现工程没有"离线产出"系统**。"挂机收益"是重新登录时**用 `stepPaused` 快进模拟最多 72 小时的真实战斗**（每帧 48ms 预算，`updateRate` 每模拟 60s 乘 1.05 放大经验与掉落次数）。这决定了服务端必须重建离线结算模型，不能照搬。 | `world.js:53-85`、`Timeline.js:179-218`、`world.loots` / `gotExp` |
| 2 | **时间系统是移植核心**。`Timeline.js`（最小堆虚拟定时器 + 倍率 + 暂停 + 快进）是整个游戏唯一的时间源；配合 MobX 的 `reaction/autorun` 实现"到点自动施法/回蓝/刷怪"。服务端化 = 把一个**可加速的虚拟时钟调度器**从浏览器搬进 Node。 | `Timeline.js`、`unit.js:454+`、`EnemyBorn.js` |
| 3 | **数据层混入行为**：183 个数据文件中 **37 个**内嵌函数（公式、hook、`effect`、`canUse`）。数据表不是纯 JSON，无法简单"搬到服务端下发"。 | `grep -rlE "=>\|function\s*\(" data/` |
| 4 | **框架侧必须自建的部分**：ionet-ts 提供 Action 路由/协议/鉴权/推送/Redis 原语，但**没有游戏主循环、没有 ORM/存档抽象、没有战斗框架**。参考实现 `idle-path-of-xiuxian` 已经把这套"框架之上还缺什么"补完过一遍，可直接抄骨架。 | 框架 `ai-docs/local-pending-work.md`、`demo-mmorpg` |

**推荐架构一句话**：`pnpm monorepo` = **共享协议包** + **平台无关的纯 TS 游戏内核（game-core，去 MobX、注入 Clock/Rng/Sink）** + **NestJS + ionet-ts 权威服务端（游戏内核跑在服务端）** + **React + Vite + Antd + MobX 表现层**（不再拥有逻辑，通过 WS 请求/推送驱动）。游戏内核被服务端独占使用，同时保留"单机模式"作为降级运行时的可能性——这是重写最大的架构红利。

**最大风险**：`unit.js`（2,362 行）+ `world.js`（755 行）的战斗模拟要**在保持数值与手感 100% 一致**的前提下从 MobX 反应式改写成可确定性重放的纯逻辑，并与服务端 tick 融合。这是整个工程 60% 以上的工作量与风险集中点。

## 2. 游戏设计拆解

### 2.1 核心循环

```
选择角色 → 进入地图 → 自动战斗（Timeline 驱动刷怪/施法/回蓝）
   → 敌人死亡 → 掉落判定（装备/材料/金币/钥匙）→ 拾取规则自动处理
   → 获得经验 → 升级/巅峰等级/技能等级
   → 装备/附魔/重铸/分解/炼金 强化
   → 推进地图/副本 → 解锁剧情 → 奖励（神力/材料/装备）
   → 离线 → 重新登录时快进模拟补收益（上限 72h）
```

**这是"自动战斗 + 掉落刷子 + 成长"型 RPG**，不是"点击器/挂机产出"型放置游戏。

### 2.2 五大门面（底部 Tab）

| Tab | 主要页面 | 功能 |
|---|---|---|
| **战斗** | `battle/Battle.js` + `UnitPanel`/`PlayerPanel`/`MapPanel` | 单位面板、实时战斗日志、地图选择、副本钥石、无尽副本、挑战队列、离线等待/跳过 |
| **包裹** | `inventory/Inventory.js`(630) / `Bank.js` / `LootRule.js` | 装备栏 + 背包网格 + 物品详情（装备/出售/锁定/开包）+ 整理 + 扩容 + 储藏箱 + 自动拾取规则 |
| **技能** | `career/Skills.js` / `Enhances.js` / `Choose.js` | 主动技能排序与升级、被动（强化）装配、职业切换 |
| **生产** | `produce/Produce.js` + `Enchants`/`Rebuild`/`Medicine`/`Decompose` | 附魔（锁定部分词缀重掷）、重铸（单条重掷）、炼金（投材料升药剂）、分解 |
| **故事** | `stories/StoryList.js` / `Play.js` / `Purchase.js` | 剧情回放、剧情 DSL 播放器、神力购买情报 |

### 2.3 系统逐项

#### 时间系统 `Timeline.js`（219 行）— 全游戏的心脏

- 基于 `PrivQueue`（最小二叉堆）的**无累积误差虚拟 `setTimeout`**。
- 时间公式：`now = (parent.now - parentCurrent) * rate + current`；根时钟 `now` 来自 `mobx-utils` 的 `now('frame')`。
- 支持 `pause()` / `resume()` / `setRate(rate)`（攻速、加速模式都靠它）。
- `stepPaused(rest)`：**离线快进**，每次调用推进 `rest` 毫秒虚拟时间并清空队列中到期的定时器，每 48ms 让出一次事件循环（原用于 `requestAnimationFrame` 分批）。
- 两级时钟：`world.timeline`（世界轴，全局）与 `world.logicTimeline = new Timeline(world.timeline)`（战斗逻辑轴，被封禁时 `setRate(0.001)`）。

> **重写含义**：只需把 `mobx-utils.now('frame')` 替换为可注入的 `Clock`（真实时间 / 虚拟时间 / 测试时钟三种实现），`Timeline` 本体是纯 TS 可移植的。这是整个移植里**性价比最高**的一块。

#### 战斗系统 `unit.js`（2,362 行）

- **阵营**：`Camps{ghost,neutral,player,alien,enemy,story,shrine}` + `CampRelation`（仇恨矩阵）+ `IsAlien`（可协助）。
- **`SkillState`**：冷却（可函数）、`canUse`（资源 `hp/mp/rp/ep/comboPoint` 足够 + 自定义回调）、`shouldUse`、`effect()`。施法有 `castTime` 则先读条。
- **`BuffState`**：`type/arg/stack/totalTime/expireAt`、周期 `effectInterval`、`hooks` 注册/注销、`compBuff` 层叠替换。
- **`Unit` 基类**：`hp/mp/rp/ep/comboPoint`（setter 夹取）、`hooks: Map<hookKey, Map<id, fn>>`。
  - **`reaction(this.canUseSkill, this.tryUseSkill)` —— 反应式自动施法，无 tick**。
  - **`autorun(() => this.timeline.setRate(this.speedRate))` —— 攻速通过子时间轴速率体现**。
  - 全属性系统是 **hook 链**：`addAttrHook(key, fn)` / `runAttrHooks(value, key, ...args)`。
- **`PlayerUnit`**：从装备/被动/强化/药剂四类来源动态注册 hook；主属性 `str/dex/int/sta` 经 hook 链得出 `maxHp/maxMp/def/atk/critRate/mf/gf` 等。
- **`EnemyUnit`**：`quality` 决定前缀词缀数量与数值膨胀（`maxHp *= 2^quality`、`exp *= 2^quality`）；无尽层 `maxHp ×1.5^(L-1)`、`atk ×1.2^(L-1)`。
- **伤害管线**（`world.sendDamage`）：护盾反射 → `willDamage`/`willDamaged` 增伤减伤 → 吸收百分比 → 护甲/抗性公式（近战 `/(1+def/200)`，其他 `/(1+resist/200)`）→ 护盾吸收 → `damaged` hook → 扣血 + `message.sendDamage`。

#### 角色与成长 `player.js`（1,367 行）

- `CareerInfo`：职业等级/巅峰等级、`expFormula` 多项式、装备栏（weapon/plastron/gaiter/ornament）、已选技能/强化。
- `InventorySlot`：统一物品模型（`position ∈ equip/inventory/build/award/bank/loot`），派生 `price/atk/def/maxHp` 等。
- `Player`：`gold`、三类背包（`inventory/buildInventory/awardInventory`）、`skillExp`、`lootRule`（按 class × 品质 的 拾取/出售/分解）、`dungeonTickets`、`careers`。
- 等级转换函数（历史包袱）：`transformEquipLevel` / `untransformEquipLevel` / `getEndlessLevel`。

#### 掉落与经济 `goods.js` + `world.loots`

- `randomEquip`：`dice = random/mfRate`，`baseQualityRate=[1,0.5,0.05,0.005,0.0005,0]` 从左找首个 `< dice` 再减一；品质 4 按 `specialRate` 抽传奇。
- `loots(loots, level, quality, showToast, noUpdateRate)`：`count = type==='maxLevel' ? 1 : ceil(rate*updateRate - random())`——**`updateRate` 就是离线时间的放大系数**。
- 拾取规则 `getLootRule(class, quality, level)` → 0 拾取 / 1 卖金币 / 2 分解材料。
- 分解产出 `dust*/piece*`，品质 ≥3 额外给神力。

#### 刷怪与副本 `EnemyBorn.js`（303 行）

- `Born` 按 `monsters` 配置用 `timeline.setTimeout` 循环刷怪，`dumpState` 保存剩余时间。
- `DungeonState` 管 `phases` 阶段，全阶段结束后按钥石数结算 `exp/loots` 并切到 `pendingMaps` 或 `outside`。
- 玩家死亡走 `onPlayerDeath` 失败路径，`rebornIn = 10 + level*0.5` 秒后复活。

#### 故事与解锁 `check.js`（117 行）

- `checkRequirement({role, career, level, atMostMaxLevel, atLeastMaxLevel, map, stories, beforeStories, $or, $and})`。
- `storiesMap` 三态：不存在 / `'task'` / `'done'`。
- `taskType: 'kill'` 通过 `game.addKillTask` 注册，敌人死亡递减；`'purchase'` 花神力完成。
- 剧情脚本是自定义 DSL（`SCENE/SAY/ASIDE/WAIT`），由 `pages/stories/Play.js` 的 `parseStory()` 逐行解析。

### 2.4 离线/挂机机制（重要）

现工程**没有 `producer` 系统**（`data/producers/index.js` 是空对象且全仓库无引用）。所谓"挂机"是：

```js
// world.js:53-70
resumeGame() {
  const totalDiffTime = Date.now() - player.timestamp - timeline.getTime();
  if (totalDiffTime > 0) {
    const diffTime = Math.min(totalDiffTime, 72 * 3600 * 1000); // 封顶 72h
    const skipTime = totalDiffTime - diffTime;
    player.timestamp += skipTime;                                 // 超出部分直接丢弃
    this.forward(diffTime);                                        // 快进模拟
  }
}
```

`forward()` → `requestPending()` 用 rAF 循环调 `timeline.stepPaused()`；非地城地图每累计 60 秒模拟时间把 `updateRate *= 1.05`；经验与掉落次数都乘 `updateRate`。玩家可点"跳过"调用 `skipForward()` 直接放弃收益。

> **这是最需要重新设计的机制**。浏览器里"快进 72 小时"可以慢慢跑（用户看着进度条）；服务端不能为每个离线玩家真的模拟 72 小时战斗。见 §8.3。

## 3. 存档、反作弊与数据层

### 3.1 存档格式

| 键 | 内容 | 生产环境编码 |
|---|---|---|
| `game` | 账号级：神力、角色栏数、`purchaseRate`、`bowelLevel`、`playerMetas`、`storiesMap`、`bank`、`medicineLevel`、`highestEndlessLevel`… | **HS256 JWT**，密钥 `'chapter5.woodElf'`（`src/logics/game.js:14`） |
| `player-${key}` | 角色级：`Player.toJS()` + `timestamp` + `worldState` | `world.stop()`：`'save' + base64(secret ‖ [md5(data‖secret) ‖ data]*)` |

`world.stop()` **是混淆不是加密**：`secret` 是每次保存随机生成并**明文前置**在存档里，仅用于分片完整性校验：

```js
// world.js:699-720（压缩表述）
const secret = md5(Date.now() + '.' + Math.random(), {asBytes:true});
const json = utf8.stringToBytes(JSON.stringify({random: Math.random(), ...data}));
json.forEach((v,i) => { json[i] = v ^ (i & 0xff) ^ 0x27; });        // XOR 混淆
for (每 16 字节分片) splits.push(md5([...chunk, ...secret]), chunk); // 完整性校验
return 'save' + base64(concat(splits));
```

> **重写含义（利好）**：服务器端用 TS 重写 `stop/start` 只需 `md5` + base64 + XOR，**无密钥依赖**，因此"导入本地存档"功能可以完整实现，不需要用户提供任何密钥。这解决了最大的迁移障碍。

### 3.2 存档迁移

- 框架已就位：`doMigrates(data)` 按 `data.migrateMap[key]` 幂等执行迁移函数，但 **`migrates = {}` 是空的**——从未发生过真实迁移。
- 实际兼容靠**隐式兜底**：`fromJS` 同时接受普通对象与 `ObservableMap`；`InventorySlot.DEFAULT_LEVEL` 给旧装备补等级；`dungeonTickets` 缺失时按地图配置补齐；`skillExp` 读取时夹到 ≤70。

### 3.3 反作弊现状

**全部在前端，且已可被绕过**：

- JWT 密钥 `'chapter5.woodElf'` 硬编码在客户端源码里 → 任何人可伪造 `game` 存档。
- `world.stop/start` 是混淆 + 自校验，密钥同样在客户端 → 可解可改。
- 所有数值计算（掉落、伤害、经验、词缀重掷）都在客户端 → 无服务端校验。

> 这正是"改成服务端权威"的**核心动机**：重写后这些计算全部搬到服务端，前端只剩渲染。

### 3.4 数据层特征

- `data/base.js` 用 `arrayToMap(arr)` 把每个模块导出的数组按 `item.key` 转成 `Record<key, Data>`。
- `data/index.js` **副作用式** `require('./packages/nightmare')` / `require('./packages/year2018')`，这些包通过 `packages/util.js` 的 `define/extend` **原地改写全局注册表**（例如给**所有**敌人的 `loots` 追加红包掉落）。

> **重写含义**：TS 化时必须把"import 顺序即行为"改成**显式注册**（`registerXxx()` 返回新表或提供明确的组装入口），否则 ES module 的求值顺序与 webpack 不一致会导致数据表差异。

- 判别的关键类型（重写需显式化）：`GoodData`（`type ∈ equip/material/junk/package`）、`MapData`（普通/地城判别联合）、`EnemyData`、`SkillData`、`BuffData`、`AffixData`/`LegendData`、`CareerData`、`RoleData`、`StoryData`、`LootEntry`。
- **hook 签名不统一**，需逐类标注 `this` 与参数：

| 来源 | 签名 | `this` |
|---|---|---|
| affix | `(effect, value) => number` | `Unit` |
| legend | `(effect, value, ...extra)` | `Unit` |
| passive/enhance/enemy/enemyAffix | `(world, value, ...)` | `Unit` / `EnemyUnit` |
| buff | `(value) => number` | `BuffState` |
| medicine | `(level, value) => number` | `PlayerUnit` |
| skill `effect/canUse/shouldUse` | 不定 | `SkillState` |

### 4.4 线协议要点（`PROTOCOL.md` 为唯一真相）

```
请求 (C→S)  { cmd, subCmd, data?, headers?, traceId?, reqId? }
响应 (S→C)  { data?, errorCode?, errorMessage?, reqId?, kind? }      // 不回显 cmd/subCmd
推送 (S→C)  { kind:'notification', type?, cmd?, subCmd?, data?, timestamp?, fromUserId? }
错误码      0/undefined=成功 400=解析失败 404=路由不存在 500=内部异常
鉴权        握手期 authenticate({headers,url}) → {userId: bigint} | null(→401)
           浏览器不能设 WS 头 → 用 ?token=<jwt>
心跳        WS 协议层 ping 浏览器不可见 → 客户端须用应用层心跳（复用 system.ping）
reqId       并发请求精确配对；无 reqId 回退 FIFO（旧协议兼容）
HTTP        POST /{prefix}/{cmd}/{subCmd}；不产生 reqId/kind；无推送能力
```

## 7. 领域层移植策略

### 7.1 去 MobX：三类改动

| 现工程写法 | 移植写法 | 说明 |
|---|---|---|
| `@observable` / `makeObservable` | 普通字段 + 显式 `markDirty()` / 快照 | 服务端不需要响应式；前端需要的是"服务端下发的快照" |
| `@computed` | 纯 getter 或纯函数（带 memo 可选） | 直接搬，无需改动 |
| `reaction(canUseSkill, tryUseSkill)`（自动施法） | **显式事件驱动**：技能冷却到期入队 → 消费队列 | 这是最需要重写的部分，见 §7.2 |
| `autorun(() => timeline.setRate(speedRate))` | 属性变更时显式 `timeline.setRate(...)` | 攻速变化点可控（装备/ Buff 变更） |
| 模块级单例 + 循环依赖 | 构造器注入 `World` / `GameState` / `Clock` / `Rng` / `BattleSink` | 打破 `world ↔ player ↔ game ↔ unit` 循环 |

### 7.2 反应式自动施法 → 显式调度队列

现工程靠 MobX `reaction` 在"任一资源/冷却变化"时立刻触发 `tryUseSkill`。服务端必须改成显式：

```ts
// 现工程（隐式、依赖 MobX 依赖追踪）
reaction(this.canUseSkill, this.tryUseSkill);

// 移植后（显式、确定性）
private scheduleSkillEvaluation(unit: Unit) {
  this.clock.setTimeout(() => {
    const skill = unit.skills.find(s => s.shouldUse());
    if (skill) { skill.effect(); this.scheduleSkillEvaluation(unit); }
    else       { this.scheduleSkillEvaluation(unit); }  // 下次冷却最短的技能到点再试
  }, unit.nextSkillDelay());
}
```

**行为一致性风险**：MobX 的依赖追踪粒度与"下次求值时间"必须逐条对照现有 `canUse/shouldUse`/冷却/回蓝/回怒的语义重测，否则战斗手感与 DPS 会漂移。**这是数值回归测试的重点**。

### 7.3 依赖注入端口

```ts
// game-core/src/ports/clock.ts
export interface Clock {
  now(): number;
  setTimeout(fn: () => void, delay: number): TimerHandle;
  clearTimeout(h: TimerHandle): void;
}
// 实现：RealClock（服务端）/ VirtualClock（离线快进 / 测试）/ FrameClock（浏览器单机模式）

// game-core/src/ports/rng.ts
export interface Rng { next(): number; fork(label: string): Rng; }
// ★ 关键：现工程到处直接用 Math.random()（掉落品质、词缀、暴击、刷怪位置…）
//   必须换成可注入、可重放的 PRNG（如 mulberry32 / xorshift），
//   否则服务端无法复算校验、单测无法稳定、离线结算无法审计。

// game-core/src/ports/battle-sink.ts
export interface BattleSink {
  damage(e: DamageEvent): void;  heal(e: HealEvent): void;  death(e: DeathEvent): void;
  loot(e: LootEvent): void;      exp(e: ExpEvent): void;    mapEnter(e: MapEvent): void;
  // 服务端实现：聚合进批次 → 经 NotificationPort 推送
  // 测试实现：收集到数组断言
}
```

现有 `message.sendDamage/sendHeal/sendDodge/sendSkillUsage/sendDeath/...` 全部改为调用 `BattleSink`。`renderMessage.js`（把消息渲染成 JSX）**留在前端**，服务端只发结构化事件。

### 7.4 数据层 TS 化

**拆分原则**：数据在 `game-core/src/data/`，服务端与（可选的）单机模式都打包这一份。

1. 为 §3.4 列出的 10 类数据定义 TS 判别联合类型。
2. 把 37 个含函数的数据文件保持"数据 + 函数"一体（函数是规则，不是可下发的配置）。
3. **删除副作用式 `extend`**：`data/packages/*` 现在直接改写全局注册表（给所有敌人追加红包掉落）。改成：
   ```ts
   export function registerYear2018(tables: DataTables): DataTables { /* 返回新表 */ }
   ```
   在加载器里显式按顺序组合，保证与 webpack 顺序一致且可测。
4. **hook `this` 绑定**用接口显式表达（见 §3.4 表），禁止隐式 `any`。

**是否下发数据给前端**：推荐**前端打包一份只读投影**（`name/description/图标/品质/价格/词缀描述`），由 `game-core` 生成，仅供展示；**所有数值计算以服务端为准**。这样既避免每次打开面板请求静态表，又不把权威计算交给前端。

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A1 服务端权威实时模拟** | 服务端对每个在线角色跑虚拟时钟 + 战斗，按 tick 推送事件；前端纯渲染 | 权威、反作弊彻底、逻辑单份 | 推送量大；服务端 CPU 与在线数线性相关；弱网体验差 | **推荐**（配合批次推送） |
| **A2 服务端权威 + 批次推送** | 同 A1，但按 200–500ms 聚合事件批次、只推"变化量 + 关键事件"，前端做插值/日志 | 推送量降一个数量级；手感接近原版 | 需要设计批次协议与前端回放 | **推荐（A1 的具体形态）** |
| **A3 客户端模拟 + 服务端结算校验** | 服务端发种子与初始状态，客户端用同一 `game-core` 模拟，上报结果，服务端用同种子复算 | 延迟最低、服务端最省 | 需完全确定性（PRNG + 固定步长）；逻辑双份运行；作弊面更大 | **降级/单机模式可用**，不作首选 |

**推荐 A2**：把现工程的 `Timeline` 原样搬进服务端，客户端保留一个"表现层 Timeline"只做动画/日志节流。因为 `game-core` 与平台无关，未来若要支持"离线单机模式"，客户端可以直接复用同一内核（即 A3 自然成立），**不冲突**。

### 8.2 决策 B：服务端 tick 的形态

框架没有 tick，参考实现用**受管 `setInterval` + 时间轮**。推荐组合：

```ts
// ① 全局心跳：固定步长推进虚拟时钟
setInterval(() => worldClock.advanceTo(Date.now()), TICK_MS);   // TICK_MS = 100~200

// ② 每角色一棵 Timeline（移植现工程），到点执行回调
// ③ 事件批次化：同一 tick 内产生的 BattleSink 事件合并成一帧推送
```

**关键约束**：`stepPaused` 的"每 48ms 让出事件循环"是**浏览器**的分批策略，服务端应改为**事件预算**：单次推进最多执行 N 个定时器回调（如 5,000），超出则记入下一轮，避免单个离线玩家阻塞事件循环。

### 8.3 决策 C：离线收益怎么算（最关键的重新设计）

现工程 = **快进模拟最多 72 小时真实战斗**。服务端不能照搬（成本不可控）。三个选项：

| 方案 | 做法 | 保真度 | 成本 | 建议 |
|---|---|---|---|---|
| **C1 有界快进模拟** | 离线时用同一内核推进，但设**时间上限 + 事件预算**（如最多模拟 30 分钟虚拟时间或 5,000 次击杀），其余按速率外推 | 高 | 中（可控） | **推荐** |
| **C2 解析式离线结算** | 用 `DPS / 敌人 HP` 估算击杀数，用 `loots` 期望值 × 击杀数 × `mfRate` 抽样掉落；经验同理 | 中（期望一致，随机分布不同） | 低 | 备选（参考实现 `TEMPORARY-OFFLINE-IDLE` 就是这类） |
| **C3 后台持续生产 Worker** | 复用 `phase5-idle-production-queue.md` + `demo-mmorpg` 的 TimingWheel，离线也在服务端持续推进 | 高 | 高（离线玩家也占 CPU） | 若玩家规模小可选 |

**推荐 C1**，理由：
1. 现工程本来就是"快进模拟"，C1 是它的**有界版本**，数值与手感最接近原版；
2. 事件预算把成本从"离线时长"解耦为"固定上限"，可预测；
3. 超出预算的部分用 C2 外推兜底，保证不会因为长时间离线而给出异常收益。

具体落地：

```ts
async function settleOffline(player, offlineMs) {
  const CAP_MS = 72 * 3600 * 1000;                 // 保持原版 72h 上限语义
  const SIM_BUDGET_MS = 30 * 60 * 1000;            // 最多真模拟 30 分钟虚拟时间
  const simulated = Math.min(offlineMs, CAP_MS, SIM_BUDGET_MS);
  const extrapolated = Math.min(offlineMs, CAP_MS) - simulated;

  const ctx = createHeadlessContext(player);        // 无 IO、无 MobX
  ctx.clock.advanceBy(simulated);                   // 有界快进（C1）
  if (extrapolated > 0) applyRateExtrapolation(ctx, extrapolated);  // C2 兜底

  const drops = ctx.sink.drain();
  await persist(player, drops);
  return buildOfflineReport(drops);                 // 前端展示"离线收获"
}
```

> **产品决策点**：原版有"跳过"按钮（`skipForward()`，放弃收益）。重写后"离线收益"变成服务端即时结算，这个按钮的语义需要重新定义（展示结算报告 vs 直接跳过）。**需要与策划确认**。

## 9. 状态、持久化与存档迁移

### 9.1 状态模型与存储选型

| 状态 | 特征 | 存储 |
|---|---|---|
| 账号（用户/JWT/会话） | 强一致、低频 | **PostgreSQL**（参考实现用 `pg.Pool` 裸 SQL + `withTransaction`，不用 ORM） |
| 角色（`Player`，含背包/技能/进度） | 单角色较大（`toJS()` 可达数百 KB）、读写频繁 | **PostgreSQL JSONB**（整档读写）+ 关键字段列（等级/战力/最后结算时间）便于查询 |
| 账号级（`game`：神力/剧情/银行/药剂） | 中频、结构化 | PostgreSQL 表或 JSONB |
| 在线会话 / 在线状态 | 高频、可丢失 | **Redis**（`RedisSessionStore`） |
| 战斗运行时（`world` units/buffs/timers） | 高频、易失 | **内存**（服务端进程内）；崩溃时按 §9.3 重建 |

**不推荐**把整个 `worldState` 每 tick 落库。只在**关键节点**持久化：进/出地图、副本结算、获得稀有掉落、离线结算、定时（如每 30s，沿用原版节奏）。

### 9.2 从 `localStorage` 到服务端

现工程的 `game.toJS()` / `Player.toJS()` 结构**尽量原样保留为服务端存档的 JSON 形状**，原因是：

- 迁移（§9.3）可以直接复用现工程的 `fromJS` 语义；
- 回归测试可以拿旧存档跑对比。

**唯一不迁**的是 `worldState`（在飞的战斗快照：单位、目标引用、定时器剩余）。理由：
- 它包含按数组下标的目标引用，且强绑 MobX/`Timeline` 内部状态；
- 玩家重新登录时"重新进入当前地图、重置战斗"是完全可接受的体验（原版的 `world.load` 本来就会 `findTarget()` 重寻目标）。

### 9.3 存档迁移（一次性导入）

这是本重写**最有价值的产品功能**，且技术可行（§3.1 证明 `world.stop` 是可逆混淆）：

```
客户端"导入存档"
  → 读 localStorage['game'] 与 localStorage['player-*']
  → 原样上传（明文 JSON 或 'save'+base64 编码都支持）
  → 服务端 packages/game-core/src/serialize/ 解析：
       · 'game' 首字符 '{' → JSON
       · 'game' 首字符 'e' → HS256 JWT 验签（密钥 'chapter5.woodElf'，保留用于兼容导入）
       · player 首字符 '{' → JSON
       · player 首字符 's' → 移植版 worldStart()（md5 + base64 + XOR，无密钥依赖）
  → 走 doMigrates（补齐为空实现）→ 写入 DB
  → 返回导入报告（角色数、等级、物品数、丢弃的 worldState 说明）
```

**移植清单**：`md5`（`md5` 包或 Node `crypto`）、`utf8`、`crypt.bytesToBase64/base64ToBytes`、XOR 循环、分片校验。**工作量小、风险低、用户感知强**，建议排在 P1（早做）。

### 9.4 安全

| 项 | 做法 |
|---|---|
| 认证 | HTTP：JWT（`Authorization: Bearer`）；WS：握手期 `authenticate` → `?token=<jwt>` |
| 授权 | 所有业务 Action 走 `requireUserId(ctx)`；`PUBLIC_ACTION_KEYS` 白名单只放 `system.ping` |
| 服务端权威 | 掉落品质、词缀重掷、伤害、经验、价格校验**全部在服务端**；前端只发"意图"（如"分解这件"） |
| 幂等 | 消耗类操作（分解/附魔/重铸/开包）带 `opId`，服务端去重，防重放 |
| 限流 | 框架 `RateLimitInOut` **无法短路**（§4.3 #4）→ 自行实现（抛错 / 自定义执行器） |
| 生产守卫 | `NODE_ENV=production` 默认拒启动，需显式 `allowProduction: true` |
| token 泄露 | `?token=` 会进访问日志 → 生产建议改为短期握手 ticket |

## 10. cmd 段与 Action 面规划

沿用参考实现约定：**一段一域、段宽 10、段内 subCmd 从 1 起、0 保留**；前端 `commands.ts` 手工镜像后端 `cmd.ts`（并在注释里声明"唯一真相在后端"）。

```ts
export const CMD_SEGMENTS = {
  system:    1,   // ping / 版本 / 公告

  battle:   40,   // 战斗状态查询 / 目标切换 / 手动技能（若保留）
  inventory:50,   // 背包 / 装备 / 出售 / 锁定 / 整理
  bank:     60,   // 储藏箱互转 / 扩容
  lootrule: 70,   // 拾取规则
  career:   80,   // 职业切换 / 技能 / 被动（强化）
  produce:  90,   // 附魔 / 重铸 / 炼金 / 分解
  story:   100,   // 剧情状态 / 完成 / 回放
  shop:    110,   // 神力商店 / 炼金重置（原 Purchase）
  idle:    120,   // 离线结算报告 / 领取

```

**推送路由**（与请求同 `(cmd, subCmd)` 命名空间，靠 `kind:'notification'` 区分）：

| 推送 | 内容 | 频率 |
|---|---|---|
| `(world, 1) world.tick` | 单位快照增量（hp/mp/buff/目标/施法条） | 5 Hz（200ms 批次） |
| `(battle, 1) battle.log` | 结构化战斗事件（伤害/治疗/闪避/死亡/掉落/经验） | 随批次聚合 |
| `(battle, 2) battle.loot` | 掉落获得（可单独弹 Toast） | 事件驱动 |
| `(player, 3) player.levelup` | 升级 / 巅峰 / 技能升级 | 事件驱动 |
| `(story, 1) story.unlock` | 可开启剧情 | 事件驱动 |
| `(inventory, 1) inventory.changed` | 背包变更（服务端权威后必须由服务端告知） | 事件驱动 |
| `(system, 2) system.notice` | 公告 / 系统消息 | 低频 |

> **注意**：现工程的 `message` 总线会产生**极高频率**的事件（每次伤害一条）。服务端必须**聚合 + 节流**（参考实现的 `OnlineNotifyService` 就是按 `pushEveryMs` 合并帧），否则 WS 会被打爆。前端 `renderMessage` 保留，消费批次。

### 11.2 状态管理

**推荐沿用 MobX，但用 `makeAutoObservable`（参考实现方案 C，零装饰器）**，理由：
- 团队/代码库已熟悉 MobX（现工程就是 MobX）；
- 零装饰器 → 避开 `useDefineForClassFields` 与 legacy decorator 的全部工具链风险（参考实现踩坑 #6）；
- 前端不需要 DI，不需要 `emitDecoratorMetadata`。

**RootStore 组合根**（照抄参考实现形态）：

```ts
class RootStore {
  client: GameClient;
  session: SessionStore;  connection: ConnectionStore;  toast: ToastStore;
  world: WorldStore;  inventory: InventoryStore;  career: CareerStore;
  produce: ProduceStore;  story: StoryStore;  player: PlayerStore;

  constructor() {
    this.client = new GameClient({
      getToken: () => this.session.token,

      lifecycle: this.lifecycle,
    });
    const ctx = { game: this.client.game, toast: this.toast, root: () => this };
    this.world = new WorldStore(ctx); /* … */
  }
  private routeNotification(n: PushFrame) {
    if (n.cmd === WORLD_CMD.cmd)     return this.world.handleNotification(n);
    if (n.cmd === INVENTORY_CMD.cmd) return this.inventory.handleNotification(n);
    /* … */
  }
}
```

**推送消费模式**（前端**只存帧、不本地推进**）：

```ts
handleNotification(frame: PushFrame): void {
  if (frame.subCmd !== BATTLE_CMD.log) return;
  const batch = frame.data as BattleLogBatch;
  runInAction(() => {
    this.units = batch.units;                 // 权威快照
    this.log.push(...batch.events);           // 追加日志
    if (this.log.length > 1000) this.log.splice(0, this.log.length - 1000);
  });
  for (const e of batch.events) if (e.kind === 'loot') this.ctx.toast.success(...);
}
```

**竞态守卫**：每个发请求的 action 先取 `token = guard.next()`，回写前 `if (!guard.isCurrent(token)) return;`（参考实现 `load-guard.ts`）。

### 11.3 传输层

**直接复用 `@nbb-ionet/client-protocol`**（浏览器安全、零 Node 依赖），上层自建 `packages/ionet-transport`：

```ts
// transport/socket-adapter.ts      平台差异唯一收敛点（只搬运原始帧）
// client/ionet-client.ts           状态机：idle→connecting→online→reconnecting→failed
// client/correlation.ts            reqId 关联（复用 client-protocol 的 Associator）
// api/commands.ts                  镜像后端 cmd.ts
// api/dto.ts                       镜像后端 DTO 类型
// api/game-api.ts                  按域组织的 typed API
// testing/                         FakeSocketAdapter + MemoryIonetServer（零后端开发）
```

**要点**（来自参考实现）：
- 心跳用应用层 `system.ping`（15s 一发、10s 未回强制重连）——浏览器观察不到 WS 协议层 ping/pong；
- 重连指数退避 + 抖动；**握手失败默认不重连**（避免 401 死循环）；
- `visibilitychange` / `online|offline` 接入生命周期；
- HTTP fallback 通道**不产生 `reqId`/`kind`**，降级即失去并发关联。

**不要**在 web 里 import 除 `client-protocol` 之外的任何 `@nbb-ionet/*` 包（其核心依赖 Node `async_hooks`，浏览器加载即炸）。

## 12. 关键决策与取舍

| # | 决策 | 选择 | 理由 | 备选 |
|---|---|---|---|---|
| D1 | 游戏内核归属 | **`game-core` 纯 TS，服务端权威运行** | 反作弊、逻辑单份、可测、可复用为单机模式 | 逻辑留在前端 |
| D2 | 战斗执行 | **服务端实时模拟 + 200ms 批次推送** | 权威且推送可控 | 客户端模拟 + 服务端复算 |
| D3 | 离线收益 | **有界快进模拟（上限 + 事件预算）+ 解析外推兜底** | 最接近原版且成本可控 | 纯解析结算 / 后台持续生产 |
| D4 | 时间源 | **可注入 `Clock`**（真实/虚拟/测试） | `Timeline` 是核心，必须可快进可测 | 保留 `mobx-utils.now('frame')`（不可行） |
| D5 | 随机数 | **可注入可重放 PRNG**，替换全部 `Math.random()` | 确定性重放、离线审计、稳定单测 | 保留 `Math.random()`（无法复算） |
| D6 | 持久化 | **PostgreSQL（角色 JSONB + 关键列）+ Redis（会话/在线）** | 参考实现验证过；框架只给 Redis 原语 | 纯 Redis / 纯 Mongo |
| D7 | ORM | **不用 ORM，裸 SQL + 事务包装** | 与参考实现一致，减少依赖与魔法 | Prisma |
| D8 | 前端状态 | **MobX + `makeAutoObservable`（零装饰器）** | 团队熟悉 + 规避装饰器工具链风险 | Zustand / Redux |
| D9 | 前端构建 | **Vite + React 18 + TS** | 参考实现验证过；需 watch-workspace-src 插件 | 保留 webpack |
| D10 | 数据下发 | **前端打包只读投影（展示用），数值计算全在服务端** | 免请求静态表 + 保证权威 | 全量下发含函数的数据 |
| D11 | `worldState` 迁移 | **不迁移，重新进入地图** | 含下标引用与定时器内部态；重进可接受 | 强行迁移（高风险低收益） |
| D12 | 旧存档导入 | **做，且排在 P1** | 技术可行（可逆混淆）、用户价值高 | 不做（用户流失） |
