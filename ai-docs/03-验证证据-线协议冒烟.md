# 验证证据 · 线协议端到端冒烟

**脚本**：`packages/server/scripts/ws-protocol-smoke.mjs`
**运行方式**（需先 `pnpm run build`）：

```bash
cd packages/server
PORT=3999 JWT_SECRET=test-secret IONET_ALLOW_PRODUCTION=true node dist/main.js &
node scripts/ws-protocol-smoke.mjs 3999 test-secret
```

> `DATABASE_URL` 可指向不可达地址：健康检查会正确返回 `503 degraded`，
> 但**线协议层的全部断言不依赖数据库**（除最后一条「已进入业务层」外）。

## 实测结果（2026-09-19）

在真实运行的 NestJS + ionet-ts 服务端（单端口 `3999`，REST `/api` 与 WS `/ws` 同端口）上：

| # | 断言 | 覆盖条款 | 结果 |
|---|---|---|---|
| 1 | 无 token 的握手被 HTTP 401 拒绝 | §6 | PASS |
| 2 | 错签名的 token 同样被 401 拒绝 | §6 | PASS |
| 3 | `?token=<jwt>` 握手成功（升级未被拒） | §6 | PASS |
| 4 | reqId 精确配对：响应回显 `reqId` 且 `kind='response'` | §4.1 | PASS |
| 5 | 响应不回显 `cmd`/`subCmd` | §4 | PASS |
| 6 | 成功响应 `errorCode` 缺失或为 0 | §8 | PASS |
| 7 | 未注册 Action → `errorCode=404` | §8 | PASS |
| 8 | 坏帧 → `errorCode=400` | §8 | PASS |
| 9 | 旧协议（不带 reqId）响应不注入 `reqId`/`kind` | §12.1 | PASS |
| 10 | 并发在途请求各自精确配对 | §4.1 | PASS |
| 11 | `system.ping` 的 `data` 为 `{success:true,data:{...}}` | 工程约定 ActionResult | PASS |
| 12 | 时钟对齐字段名固定为 `serverTime` | 工程约定 | PASS |
| 13 | `system.version` 含 `protocolVersion`/`serverTime`/`wsPath` | 工程约定 | PASS |
| 14 | 带 token 时 `auth.me` 已进入业务层（非 401/404） | 鉴权链路 | PASS |
| 15 | 业务失败为 `errorCode=0` + `data.success=false` + `data.data.code` | **两级错误判定** | PASS |

**15/15 通过。**

> 第 11–13 条是**跨包契约回归**：`@idle-dark/protocol` 的 `SystemPingDto`/`SystemVersionDto` 与
> 服务端 `HealthAction` 的返回必须一致，客户端 typed API（`SystemApi`）与
> `extractServerTime()` 才可用。

## 关键证据原文

```
PASS  §4.1 reqId 精确配对：响应回显 reqId 且 kind=response
      —— {"data":{"success":true,"data":{"status":"ok","service":"idle-dark-forever","serverTime":1789813461255}},"reqId":"r-1","kind":"response"}
PASS  §8 未注册 Action → errorCode=404
      —— {"errorCode":404,"errorMessage":"Action not found for cmd=999, subCmd=9","reqId":"r-2","kind":"response"}
PASS  §12.1 旧协议响应不注入 reqId/kind
      —— {"data":{"success":true,"data":{"status":"ok","service":"idle-dark-forever","serverTime":1789813461266}}}
PASS  约定 ActionResult：system.version 含 protocolVersion / serverTime / wsPath
      —— {"success":true,"data":{"serverVersion":"0.1.0","protocolVersion":1,"serverTime":1789813461270,"wsPath":"/ws"}}
PASS  两级错误判定：业务失败为 errorCode=0 + data.success=false + data.data.code
      —— {"success":false,"message":"服务器开小差了，请稍后再试","data":{"code":"INTERNAL","detail":{"reason":"connect ECONNREFUSED 127.0.0.1:1"}}}
```

最后一条的 `INTERNAL` 由数据库不可达触发 —— 这**正是期望**：它同时证明了
① 请求已穿过 WS 握手鉴权与 Action 路由到达业务层（若鉴权失效会得到 401，若路由失效会得到 404）；
② 服务端把基础设施异常规范化成**业务失败**（`errorCode=0` + `success=false` + 机器可读码），
而不是抛裸 500 —— 前端因此能走统一的两级错误判定并展示可读文案。

## 健康检查行为

`GET /api/health` 在数据库不可达时返回 **503** 与结构化降级信息（非 500 崩溃）：

```json
{"status":"degraded","service":"idle-dark-forever","uptimeSeconds":3,
 "checks":{"database":{"status":"down","latencyMs":0,"error":"connect ECONNREFUSED 127.0.0.1:1"}}}
```
