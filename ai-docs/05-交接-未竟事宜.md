## 1. ✅ 已修复：拾取规则「自动出售/分解」不生效

**症状**：面板里设置「某类装备某品质 → 出售/分解」后，战斗掉落仍走 `minLootLevel` 兜底规则，
面板设置**完全不起作用**。

**根因（当时逐行确认，两侧键与值类型都不匹配）**：

- 面板侧编码（原 `server/.../inventory/internal/loots.ts`）：
  ```
  player.lootRule: Map<string, number>
     '__enabled__'                  → 1 | 0          （全局开关）
     `c:${class}:${quality}`        → action | action+10（停用则 +10）
  ```
- 战斗侧读取（原 `game-core/src/combat/battle-world.ts:553-565`）：
  ```ts
  const rule = this.player?.lootRule?.get(clazz);   // ← 按 class 取，取不到（键是 c:class:quality）
  const value = rule && rule[quality];              // ← rule 是 number，再索引 quality 必然 undefined
  // → 永远返回 0，于是继续走 minLootLevel
  ```
- 还有一个**被类型谎言掩盖**的问题：`combat/player-unit.ts` 的 `PlayerLike.lootRule` 被标成
  `Map<string, Record<number, number>>`（照抄原版 `Map<class, number[]>`），而 `Player.lootRule`
  实际是 `Map<string, number>` → `tsc` 完全看不出编码错配。

**已做的修法（采用"编码下沉 game-core 成为唯一定义"）**：

1. 新增 `packages/game-core/src/rules/loot-rule.ts`：`LootRuleAction` / `LOOT_RULE_ENABLED_KEY` /
   `LOOT_RULE_PREFIX` / `LOOT_RULE_DISABLED_OFFSET` / `lootRuleKeyOf` / `parseLootRuleKey` /
   `encodeLootRule` / `decodeLootRule` / `lootRuleEnabledOf` / `lootRuleActionOf`，并从
   `rules/index.ts` 导出（`game-core` 公共出口自动带出）。
2. `combat/battle-world.getLootRule()` 改为**单行委托** `lootRuleActionOf(this.player, …)`。
3. `server/.../inventory/internal/loots.ts` 删除本地那份编码/判定，改从 `@idle-dark/game-core` 引入；
   `lootrule/internal/loot-rule-ops.ts` 也直接引 `game-core`（面板只读写状态）。
4. `PlayerLike.lootRule` 类型改为 `ReadonlyMap<string, number>`。
5. **顺带修掉一个同链路的真 bug**：`world/internal/player-like.ts` 的 `lootRecorder` 在
   `player.loot(slot)` **之后**读 slot，而 `Player.loot` 会 `clear()` 它 → `(battle, loot)` 推送
   一直是空槽（`{key:null,count:0}`、`dto.gold` 丢失）。改为**先快照再落地**。

**验证（全部已实跑）**：

- 单测：`game-core/src/rules/loot-rule.test.ts`（19 例：key 编解码 / `+10` 停用边界 /
  `undefined`·`NaN`·`Infinity`·字符串 / 全局开关 / `minLootLevel` 边界 / 空 class）。
- 集成：`game-core/src/combat/loot-rule.test.ts`（10 例：从 `loots()` 一路断言到 `BattleSink.loot`
  事件的 `sell`/`decompose`/`pickup`）。**用旧实现跑会挂 5/10**，已实测。
- 服务端：`server/test/world-loot-rule.test.ts`（6 例：`opUpdateLootRule` 面板写入 → `toPlayerLike`
  → 真实 `RulesLootService` → `Player.loot` 落地）。**去掉快照修复会挂 2/6**，已实测。
- 端到端：`server/scripts/loot-rule-smoke.mjs`（真实 REST+WS+DB：注册 → 建角色 → 完成
  `eyer-stories-1` → 面板规则全设"出售" → 落库往返复核 → 进 `town.street` → 观察
  `(cmd=40,subCmd=2)` 掉落推送）。本地以 `LOOT_WINDOW_MS=300000` 实跑 **18/18 通过**，
  其中抓到一次真实装备自动出售：
  `{"slot":{"key":"gold","count":10,...},"handled":"sell","gold":10}`，
  且同期 `inventory.list` 里除已装备的「细木剑」外**没有多出任何装备**（确实被卖掉而非入包）。

**残留注意**：装备掉率是概率性的（`slime.minimal` 装备 0.1/kill），冒烟里那一项在窗口内没掉出装备时
记 SKIP 而非 FAIL（避免 CI 抖动）；`LOOT_WINDOW_MS` 可调（默认 90 s）。**该脚本未接入 CI**（要跑数分钟），
CI 的门禁由上面那批确定性单测/集成测试承担。

## 2. ✅ 已修复：纯剧情脚本的「进图自动播放」（以及击杀任务的静默登记）

**症状**：原版里「到达满足条件的地图即自动播放该图剧情」（`MapPanel.checkStories()`），
现在必须玩家自己到「故事」页点一下。
**更严重的是**：原版进图时会把 `kill` / `purchase` 类剧情**静默登记**为进行中并挂上击杀任务；
移植版只在玩家手动 `story.play` 时才登记 → 玩家不去点，打怪**完全不计进度**，主线直接卡死。

**已做的修法**（对照 `dark-forever-memorize/src/pages/battle/components/MapPanel.js:140-248`）：

1. `story/internal/story-ops.ts` 新增 `opAdvanceStoriesOnMapEntry(tables, player, extras, map)`
   与 `registerStoryTask(extras, story)`：
   - `kill` / `purchase` → 登记为 `task`（击杀任务挂 `killCount`），返回进 `tasks`；
   - 纯剧情脚本 → **不改状态**，返回进 `scripts`（打开时才置 `task`）。
   **幂等**：登记过的因 `status !== 'none'` 跳过，重复进图不会把击杀进度重置回满。
2. `opFinishStory` 用同一套分类：新就绪的 `kill`/`purchase` **当场登记**、纯剧情脚本上报
   （对应原版 `checkStories()` 的 `while (dirty)` 循环）。`opPlayStory` 复用 `registerStoryTask`。
3. `WorldService.start()`（会话首次落地在该图）与 `WorldService.enterMap()` 调用它，
   并推 `(story, unlock)`；`onEnemyKilled` 在剩余击杀数降到 0 时也推一次。
4. 推送载荷冻结为 `StoryUnlockDto`（`protocol/src/dto.ts`）：`{ key, name, taskType, autoPlay }`。
   `autoPlay=true` = 纯剧情脚本刚可开启 / 击杀任务刚达成。
5. 前端：`web/src/stores/ui-store.ts`（新）把「当前面板 key」从 `GameShellPage` 的局部 state
   提升为 Store —— 否则推送驱动的跳转无处发起；`story-store.handleNotification` 依据 `autoPlay`
   决定是否 `open()`，打开前先切到「stories」面板，玩家正在读别的剧情时不打断。

**验证（全部已实跑）**：

- 单测：`server/test/logic/story/story.test.ts` +9（进图推进/幂等/地图不匹配/解锁分类）；
  `server/test/world.service.test.ts` +4（start 推剧情 1、进图推剧情 2、登记剧情 3 击杀任务、
  击杀达成推送且不重复）。
- 集成：`web/test/integration.test.ts` +5（autoPlay 自动打开并跳面板、autoPlay=false 不跳、
  读剧中不打断、已完成不打开、载荷缺 key 安全忽略）；`web/test/unit.test.ts` +3（`UiStore` 边界）。
- 端到端：`server/scripts/story-entry-smoke.mjs`（真实 REST+WS+DB）**14/14 通过**，
  实测链路：进 `town.street` → 收到 `eyer-stories-2`（`script`/`autoPlay=true`）→ 完成它 →
  收到 `eyer-stories-3`（`kill`/`autoPlay=false`）→ `story.list` 显示 `status:'task'`、`remaining:10`。

端口与代理地址的**唯一真相**是仓库根的 `dev.config.json`（前端 `vite.config.ts` 直接 import，
后端 `scripts/dev.mjs` 读它并写进 `process.env.PORT`）。因此命令里**不再需要**端口参数：

```bash

pnpm dev           # 两者一起（--parallel）
```

临时换端口不改文件：`PORT=3200 pnpm dev:server`、`VITE_DEV_PORT=5300 pnpm dev:web`、
`VITE_BACKEND_ORIGIN=http://127.0.0.1:9999 pnpm dev:web`。
