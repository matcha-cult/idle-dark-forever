# 容量基准与并发上限（实测）

> 用途：制定后续迁移任务书时的**量化基线**。所有数字都是本机实测，脚本路径一并给出，
> 可复跑。**没有这些数字，"撑多少人"只能是猜。**

## 0. 一句话结论

**战斗 CPU 不是瓶颈（5000 人只占单核 6%）；真正会先崩的是三处"当初没设上限"的地方：**

1. **调度轮转上限** `maxCharactersPerTick = 100` → 5000 人在线时每个角色 **每 10 秒才 tick 一次**，
   每次最多补 5 秒虚拟时间 ⇒ **世界时间只有真实时间的 ~50%**，且快照从 5 帧/秒退化成 **10 秒一帧**；
2. **每 tick 推全量 units 快照**（实测 783 B/帧 × 5 Hz）→ 5000 人 ≈ **19 MB/s**，单位多的图线性放大到 ~100 MB/s；
3. **单进程单事件循环 + 纯内存会话**（`redis: false`，推送是进程内扇出）→ 无法水平扩展；
   且**离线会话不回收**。

## 1. 实测数据

### 1.1 战斗 tick 的 CPU（每角色每 200ms 虚拟时间）

方法：真实数据表 + 真实 `BattleWorld`，与 `WorldService.tickSession` 同样的调用方式
（`clock.pause()` 后 `stepPaused(200ms, budget=2000)`），先跑 60s 虚拟时间到稳态再计时。

脚本：`ai-script/bench-combat.mjs`、`ai-script/bench-maps.mjs`（**已入库**）

| 地图 | 稳态单位数 | µs / 角色 / tick | 折算 5000 角色一轮 |
|---|---|---|---|
| `home`（无怪） | 1.0 | **0.64** | 3.2 ms |
| `town.street` | 3.0 | **1.43** | 7.2 ms |
| `town.woods` | 6.0 | **1.44** | 7.2 ms |
| `town.valley` | 6.0 | **2.47** | 12.4 ms |

- 单位成本 ≈ **0.3–0.5 µs / 单位 / tick**（成本随单位数与战斗事件数线性增长）。
- 5000 角色 × 6 单位 ≈ **12.5 ms / 200ms 轮** = 单核预算的 **~6%**。
- ⚠️ 冷启动（JIT 未热）时同一基准量为 1.7–9.25 µs/角色，做容量规划要用稳态值。
- ⚠️ 该基准的事件密度很低（`town.street` 约 25 个事件/分钟）。**高等级 AoE / 无尽副本**会显著更高。

### 1.2 `(world, tick)` 推送帧大小（真实服务器实测）

脚本：`packages/server/scripts/frame-size.mjs`（**已入库**；需 3100 在跑）

```
{"units":1,"unitsBytes":266,"ticksSeen":59,"avgTickBytes":783,"maxTickBytes":1055,
 "perPlayerKBps":3.8,"for5000_MBps":18.7}
```

- 单帧 avg **783 B** / max 1055 B（含 `units` + `events` + 收益增量）；`units` 约 **200–300 B/单位**。
- 5 Hz ⇒ **3.8 KB/s / 人**；5000 人 ⇒ **~19 MB/s ≈ 150 Mbit/s**（长期持续）。
- 单位数 15 时线性放大到 **~100 MB/s ≈ 800 Mbit/s** ⇒ 单机网卡级别的墙。

### 1.3 会话内存

脚本：`ai-script/bench-mem-payload.mjs`（200 会话 `heapUsed` 增量 / 会话）

- **~33 KB heap / 会话**（2 单位）⇒ 5000 会话 ≈ **165 MB**，再加 `Player` / `PlayerContext` /
  采集器 / `account_state` 缓存，量级 **~0.5 GB**。**可接受。**

### 1.4 DB 写入

`persistIntervalMs = 30_000`（`world.config.ts:22`）⇒ 5000 人 ≈ **167 次全量 `characters.state` jsonb 写/秒**
（每笔数十 KB）。`maybeFlush()` 每 tick 调一次但只写脏角色。**需要批量 upsert 或只写脏字段。**

## 2. 上限都在哪（`world.config.ts`）

| 常量 | 值 | 现状后果 |
|---|---|---|
| `tickIntervalMs` | 200 | 设计 5 Hz，与 `NotificationBatcher.flushIntervalMs` 一致 |
| `maxCatchUpMs` | 5_000 | 单次最多补 5s 虚拟时间；**与轮转上限叠加后造成世界半速** |
| `callbackBudgetPerCharacterPerTick` | 2_000 | **每角色**预算，**没有全局上限** → 最坏 5000×2000 = **1000 万回调/轮** |
| `maxCharactersPerTick` | 100 | 🔴 每轮只轮转 100 个角色；5000 人在线 ⇒ 每角色 **0.1 次/秒** |
| `persistIntervalMs` | 30_000 | 见 §1.4 |

**5000 人在线时的推演**（`world.service.ts` 的 `tick()`）：

```
每轮 tick 100 个（tickCursor 轮转） → 每角色被 tick 5×100/5000 = 0.1 次/秒（10 秒一次）
elapsed ≈ 10s → rest = min(10s, maxCatchUpMs=5s) = 5s
⇒ 每 10 秒真实时间只推进 5 秒世界时间 → 世界时间 ~50% 速度，且 carryMs 持续背账
⇒ 该玩家的 (world,tick) 快照 = 10 秒一帧（而不是 5 帧/秒）
```

这不是"慢"，是**功能坏掉**。数百人在线时（≤100）该轮转仍能让每人 200ms 一次，所以从来没暴露。

## 3. 撑 5000 同时在线的改造清单（按性价比排序）

1. **调度改为预算驱动（必须先做）**
   - 把"每轮最多 N 个角色"换成"**每轮跑满 X ms 或全局回调预算就停**，下轮从 `tickCursor` 继续"，
     保证每个在线角色稳定 ~200ms 一次；
   - `callbackBudgetPerCharacterPerTick` 之外增加**全局**每轮回调上限；
   - 超载时的降级策略要显式化（见 §4.7）。
2. **推送降本（最大一笔带宽）**
   - `world.tick` 由"每轮全量 units"改为**增量**（只推变化单位/血量/目标），或快照降到 1–2 Hz、
     战斗事件仍即时；预计 egress 降一个数量级。
3. **拆进程 + 粘性路由 + Redis**
   - `node:cluster`/多实例，同一角色固定落同一 worker（否则 world 会话在内存里会撕裂）；
   - 打开框架的 `redis: true`（`app.module.ts` 现在是 `redis: false`，推送只在本进程扇出）。
4. **DB 批量化**：多人一次 upsert、只写脏字段、落库间隔按在线人数自适应。
5. **会话生命周期**：空闲会话回收（离线 > N 分钟 → `stop()`）+ 会话数上限。

## 4. 「一开始没做限定」——新任务书必须先拍板的参数

这几项**先定，再改代码**；每项都要给出取值 + 超载时的行为：

| # | 参数 | 现状 | 必须先定 |
|---|---|---|---|
| 1 | 目标同时在线（常态/峰值） | 未声明 | 例：常态 500 / 峰值 5000 |
| 2 | 每角色战斗 tick 频率 | 200ms（5 Hz） | 是否允许按人数降级？降到多少仍可接受 |
| 3 | 快照推送频率与形态 | 5 Hz 全量 | 增量 or 1–2 Hz 全量 |
| 4 | 单机上限 vs 多实例 | 单进程 | 是否接受粘性路由 + Redis |
| 5 | 单角色 CPU / 内存配额 | 无 | 例：≤50 µs/tick、≤100 KB/会话 |
| 6 | DB 写入预算 | 30s/人全量 | 每角色行大小上限、批量粒度 |
| 7 | **超载降级规则** | 无（当前是静默变慢/半速） | 降频？降精度？拒新连接？必须显式且可观测 |

**核心教训（写进新任务书）**：任何"每轮处理 N 个"的循环都要同时给出**全局预算**与**超载行为**，
否则人数一超限就不是"变慢"，而是**世界时间与真实时间脱钩**（本次就是 `maxCharactersPerTick=100`）。

node --expose-gc ai-script/bench-mem-payload.mjs

# 推送频率自检（浏览器 Console，dev-only）
