## 0. 一句话根因与必须写成不变式的结论

本次迁移暴露的根本问题不是某个 bug，而是**一开始没有对并发做限定**：没有先定
「同时在线目标 / 每角色 tick 频率 / 快照频率与形态 / 单机还是多实例 / 每角色 CPU·内存·DB 预算 / 超载降级规则」。

后果已实测：`maxCharactersPerTick = 100` 这类「每轮处理 N 个」的循环**不报错**，
而是让**世界时间与真实时间脱钩** —— 5000 人时每个角色 10 秒才 tick 一次、每次最多补 5 秒
⇒ 世界约 50% 速度、快照退化成 10 秒一帧。而战斗 CPU 只占单核 6%，
真正的墙是**调度上限、每 tick 全量快照的带宽、单进程无机/粘性路由**。

### 不变式（施工与验收的红线）

| # | 不变式 | 判据 |
|---|---|---|
| I1 | **世界时间 = 真实时间**（每个在线角色 `Σ推进虚拟时间 / Σ真实经过时间 ≈ 1`） | 指标 `world_time_ratio ≥ 0.99`，低于即告警 |
| I2 | **任何「每轮处理 N 个」的循环必须同时给出全局预算与超载行为** | 代码评审项；无超载行为的截断一律视为缺陷 |
| I3 | **禁止静默降级**：一切降频 / 截断 / 丢弃必须同时产出**日志 + 指标 + 明确动作** | 日志含 `[OVERLOAD]`；指标 `overload_level > 0`；帧带 `degraded:true` |
| I4 | **CPU 不是瓶颈，不得用"少 tick 几个角色"换吞吐** | 5000×6 单位实测仅 6% 单核；降级只允许降**推送/落库**，或降 **tick 粒度**（不降 world time）|
| I5 | 每个新限额都必须能在 `/api/metrics`（或 `system.stats`）上**看到当前值** | `§3` 指标表 |

## 2. 「限定」怎么落成可观测（对应交付要求 c）

### 2.1 指标表（新增 `GET /api/metrics`；dev 另留 `system.stats` WS Action）

> 全部为**进程内累计/瞬时**值；命名 `snake_case`；无数据时不得输出 `NaN/Infinity/负数`。

| 指标 | 含义 | 设计值/告警线 | 直接对应 |
|---|---|---|---|
| `world_tick_round_duration_ms{p50,p95,max}` | 单轮 tick 墙钟耗时 | p95 ≤ 40 ms | P5 |
| `world_tick_round_chars_processed` | 本轮实际处理角色数 | 在线数时 = 在线数 | P1/P2 |
| `world_online_characters` / `world_sessions_total` | 在线角色数 / 会话总数（含离线未回收） | 差值持续变大 = 需 L3 | P1/P5 |
| **`world_time_ratio{min,p50}`** | **每角色 `Σ推进/Σ经过`（1 轮滑动窗）** | **≥0.99；<0.995 告警** | **I1（反静默半速）** |
| `world_callback_used_per_round` / `world_callback_budget` | 全局回调用量/预算 | 用量 ≤ 预算 | P5 |
| `world_truncated_ms_total` | 被截断丢弃的虚拟毫秒 | **必须恒为 0**（>0 即缺陷） | I2/I3 |
| `push_pending_frames` / `push_pending_users` | 待发帧/用户数 | 队列深度阈值触发 L1 | P3 |
| `push_dropped_total` / `push_resync_total` | 丢弃帧/触发重拉次数 | 不应随在线人数线性增长 | P3/P7 |
| `push_frames_per_sec` / `push_frame_bytes_avg` | 推送速率与平均帧大小 | 6 单位图 avg ≤200 B、单人 ≤1.0 KB/s | P3 |
| `persist_writes_per_sec` / `persist_dirty_backlog` / `persist_batch_size` | 落库速率/积压/批量 | ≤20 次/s、积压阈值触发延长 | P6 |
| `admission_rejected_total` / `admission_online` | 拒新连接数/当前在线 | L4 触发与恢复 | P1/P4 |
| `overload_level` / `overload_reason` | 当前降级级别(0–5)/原因 | >0 即须有 `[OVERLOAD]` 日志 | P7 |
| `session_reaped_total` / `session_idle_ms_p50` | 空闲回收数/空闲时长 | L3 生效证据 | P5/P7 |

### 2.2 超载降级阶梯（显式、带阈值与迟滞）

| 级 | 触发条件（进入 / 退出） | 动作（可观测） |
|---|---|---|
| **L0 正常** | — | — |
| **L1 推送降频** | `push_pending_frames` 超阈值或 `world_time_ratio` 逼近 0.995 | keyframe 1 Hz → 0.5 Hz；帧 `degraded:true`；打点 `overload_level=1` |
| **L2 事件优先** | L1 持续且队列继续增长 | 暂停单位增量，只推事件 + 1 Hz keyframe；前端提示"降级中" |
| **L3 加速回收** | `world_sessions_total - world_online_characters` 超阈值 | 空闲会话回收阈值下调（如 15 min → 3 min，先 flush 再删） |
| **L4 拒新连接** | 单实例在线 ≥ 准入上限（2000），或全局回调预算连续 N 轮打满 | 握手拒绝（明确错误码）+ `admission_rejected_total++` + `[OVERLOAD]` 日志 |
| **L5 tick 粒度降级** | L4 后仍无法满足 I1 的极端情况 | 粒度 200 ms → 400 ms；`rest` 仍取完整 elapsed；`world_time_ratio` 保持 ≥0.99 并标注 `degraded` |

**迟滞**：退出阈值低于进入阈值（例如进入 80%、退出 60%），且需连续 N 轮低于退出阈值才降级，
避免抖动。**任何一级都不允许"少 tick 几个角色"或"截断 elapsed"**（`I2`/`I3`）。

## 6. 风险与未知

| 风险 | 影响 | 缓解 |
|---|---|---|
| 增量推送的客户端状态一致性 | 最易漏的是 resync 路径（`baseSeq` 断裂 / 丢帧重拉） | `PUSH_MODE=full` 可一键回滚；store 单测做随机序列与全量对拍 |
| 粘性路由依赖框架缺口 | 可能阻塞 `C1` | 先做前置调研（T-C1）；缺能力回 ionet-ts 仓库补，本仓不改 vendor |
| `redis:true` 后与本地 batcher 重复投递 | 同一 tick 多帧（`AGENTS.md` §14 已记录过重复投递现象） | cluster 冒烟断言 `serverTime` 不重复；必要时按 `(userId,serverTime)` 去重 |
| 世界时间债务记账写错 | 反而造成回放风暴 / 内存增长 | 必须有硬上限（`worldTimeDebtShedMs`）+ 显式处置 + 上限边界单测 |
| 批量落库的事务语义 | 部分失败留下不一致 | 明确"整批事务"或"逐行幂等"二者之一并写进测试 |
| `load-sim` 与真实 WS 负载差异 | 合成会话可能低估事件密度 | 保留真实 `frame-size`/`bench-*` 复跑（06 §5）；AoE/高事件密度场景补一档压力 |
