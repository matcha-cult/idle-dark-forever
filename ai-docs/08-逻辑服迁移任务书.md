## 0. 结论先行：三个必须先让用户知道的硬事实

### 事实 1：ionet 的"逻辑服"首先是**模块边界**，其次才是进程

官方知识库（stable 权威层）明确规定：

- **一个 `LogicServer` 对应一个业务模块**；命名 `XxxLogicServer`，放在该模块**根包**，
  只实现 `settingBarSkeletonBuilder(...)` / `settingServerBuilder(...)` 两个 builder 方法
  （`rules/logic-server-rules.md`）。
- **`LogicServer` 类里不许写业务**：业务只属于 `Action`（`@ActionController`/`@ActionMethod`）。
  知识库原文：*"`LogicServer` must not directly implement business flow that belongs in `Action`"*。
- 部署上是**同进程多逻辑服**与**独立进程逻辑服**两种都支持：
  `OneApplication.setLogicServerList([...])`（同进程）或每个模块一个 `*Application`（独立进程）
  （`stable/concepts/local-multi-process-deployment-concept.md`）。

> ⇒ 所以"把战斗迁移到战斗逻辑服"= 建立 `battle` 模块边界 + `BattleAction` 路由 + `BattleCmd`/`BattleMessage`
> + 战斗运行时不依赖其它逻辑服内部实现。**不一定等于"战斗单独一个进程"** —— 进程是后续部署选项。
> 这也正是我们做增量迁移的机会：**先落边界（可立即做），再落进程（依赖框架）**。

### 事实 2：TS 框架（`ionet-ts`）**没有**逻辑服运行时，且 Redis 尚未接入推送

对 `/home/nbb/projects/ionet-ts` 的实测审计结论：

| 能力 | Java 原版 `ionet/` | TS 移植 `packages/` |
|---|---|---|
| `LogicServer` 抽象 + `LogicServerApplication` | 有（`net-server`、`net-logic-server`） | **不存在**（`packages/*/src` 0 命中） |
| `ServerBuilder`（id/name/tag/cmdMerges）+ 注册表 | 有（`net-server`、`LogicServerManager`） | **不存在**；`InstanceManager` 只有自由 metadata |
| 跨逻辑服 `call`/`send`/`callCollect` | 有（`LogicCommunication` 等） | **不存在**；`FlowContext` 只有 userId/cmdInfo/request/response/session，无任何跨服方法 |
| 外部服→逻辑服转发 | 有（`CmdRegions` + 负载均衡） | **不存在**；`HttpExternalServer`/`WebSocketExternalServer` 直接 `skeleton.execute(...)` 本地执行 |
| `OnExternal`（逻辑服→对外服） | 有 | **不存在** |
| 分布式 EventBus | 有 | **不存在**（`extension-domain-event` 仅进程内） |
| `center` 发现 | 有（`net-center`） | **明确不做**（`migration-strategy.md` 写"❌ 不做"） |
| Redis 的角色 | 无（用 Aeron IPC） | 有 pub/sub/session/房/锁，**但 `extension-nestjs` 里 `redis` 只负责 `connect()`**；广播恒为 `MemoryBroadcaster`，`redis` 不参与推送（`ionet.module.ts:47-59`）；且 `redis` 只接受对象或 `false`，**不接受 `true`** |

> ⇒ **今天无法把战斗/物品/任务/角色拆成真正的独立逻辑服进程。** `demo-cluster` 也不是这个拓扑：
> 它是 N 个**完全相同的对外服实例**（每个实例什么 Action 都有），只在游戏 demo 里用应用层 Redis 频道通信。
> 框架侧必须先补 `G1–G9`（见 `§4 阶段 6`），且这些改动属于 **ionet-ts 仓库**，
> 本仓硬约束禁止改 `vendor/ionet-ts/`（`AGENTS.md` §6）。
> ✅ **A2 已拍板**：当前只做单进程边界；框架运行时交**另一会话**，证据包已写入
> `ionet-ts/ai-docs/logic-server-runtime-requirements.md`。

### 事实 3：本仓现在**拆不开**——有三条真实循环依赖 + 单一可变聚合根

对 `packages/server/src` 的实测：

- **唯一强连通分量 `{world, story, inventory}`**，即三条环：
  - `world → story`（`world.service.ts:44` 调 `opAdvanceStoriesOnMapEntry`）↔ `story → world`
    （`story.logic.service.ts:17,51-53` 用 `WorldService.positionOf`）
  - `world → inventory`（`world.service.ts:42,43` 用 `PanelCharacterService`、`pushStoryUnlock`）↔
    `inventory → world`（`inventory.logic.service.ts:17,203` 用 `WorldService.markCombatDirty`）
  - 组合环 `world → story → inventory → world`
- 潜在成环点：`career → world` 已存在，而 `career.notifyLevelup` 的注释写着"供 world 调用"——
  **一旦接线立刻成环**（`career.logic.service.ts:117-125`）。
- **所有域读写同一份可变 `Player`（`characters.state` 整份 JSONB）与同一个 `PlayerAccountState`**；
  库只有 3 张表（`users`/`account_state`/`characters`），**没有 `game_*` 表**，按表拆库不可行。
- 关键进程内状态：`WorldService.sessions/activeByUser`、`OnlineSessionService.lastSeenAt`、
  `PanelCharacterService.active`、`PlayerContextService.cache/accounts`（**无版本号，后写覆盖先写**）、
  `NotificationBatcher.queues/mergers`、`OpIdempotencyService.entries`、`RateLimiterService.buckets`。

> ⇒ 直接物理拆进程会立刻踩到：在线判定失真、会话归属撕裂、丢更新、幂等失效、推送合并器丢失。
> **必须先做"解环 + 公共层上移 + 状态单一写者"，再谈边界，最后才谈进程。**

## 2. 目标逻辑服划分与依赖方向（含解环）

### 2.1 目标拓扑（阶段 2 之后、单进程内；阶段 7 可平滑升为多进程）

```
                  ┌──────────────────────────────────────────────┐
   客户端 ──WS/REST──►│ external（对外服）                            │
                  │  握手鉴权 / 路由 / 在线集合 / 会话归属 / 推送汇聚   │
                  └───────┬──────────────┬──────────────┬─────────┘
                          │ call/send    │              │
                  ┌───────▼──────┐ ┌─────▼──────┐ ┌─────▼──────┐
                  │ battle 逻辑服 │ │ item 逻辑服 │ │ quest 逻辑服│
                  │ tick/伤害/经验│ │ 背包/银行/  │ │ 剧情/任务/  │
                  │ 掉落判定      │ │ 商店/生产/  │ │ 击杀进度    │
                  │              │ │ 拾取规则    │ │            │
                  └───┬──────────┘ └─────┬──────┘ └─────┬──────┘
                      │  events          │               │
                      └──────────► character 逻辑服 ◄────┘
                                   角色/属性/职业/选角
                          │
                  ┌───────▼──────────────────────────────┐
                  │  shared（协议/时钟/序列化/端口，无业务）  │
                  └──────────────────────────────────────┘
```

### 2.2 域 → 逻辑服映射

| 逻辑服 | 拥有的域/文件 | 拥有的状态 | 对外暴露 | 出去的事件/调用 |
|---|---|---|---|---|
| **external 对外服** | `app.module.ts` 握手鉴权、`modules/auth`、`modules/health`、`modules/edge`、`OnlineSessionService`、`PanelCharacterService`、`NotificationBatcher`、路由表 | 在线集合、当前角色、WS 连接、推送队列 | 全部客户端路由 | → 各逻辑服 `call/send`；`OnExternal` 推送 |
| **battle 战斗** | `modules/logic/world/**`、`modules/logic/battle/**`、`game-core/src/combat/**`、`world.config.ts` | 战斗会话内存态、tick、战斗种子；写 `characters.state` 的战斗切片 | `battle.*` Action（含**伤害判定/经验获取/掉落判定**入口） | → item `DropLanded`；→ quest `EnemyKilled`/`MapEntered`；→ external 推送帧 |
| **map 地图**（续篇 [09](09-地图与秘境逻辑服.md)） | 开放世界控制器：地图目录/解锁判定（`checkRequirement`）、位置与世界种子、`map.enter/leave/list/snapshot`、开放世界会话的建/切/关决策 | `world/internal/map-dto.ts`、位置/种子解析；**不持有战斗单位** | `map.*` | → battle `StartSession/SwitchMap/CloseSession`（命令）；→ quest `MapEntered`（事件）；→ character `PersistPosition` |
| **dungeon 秘境**（续篇 [09](09-地图与秘境逻辑服.md)） | `isDungeon` 挑战的控制器：票校验与**唯一扣费**（进图扣一次）、`group`、挑战队列 `pendingMaps`、相位推进决策、通关/死亡结算、`outside` 返回 | `spawner.DungeonState.switchToPhase` 决策、`battle-world` 的 `pendingMaps`、`world.service.ts:636-643` 扣票 | `dungeon.*` | → battle `StartRun/NextPhase/ExitToMap`（命令）；← battle `RunEnded/PhaseCleared`（事件）；→ character `CostTicket/PersistPosition` |
| **item 物品** | `inventory`、`bank`、`shop`、`produce`、`lootrule` | 背包/装备/银行/药剂/词缀/拾取规则；写 `characters.state` 物品切片 + `account_state.data.bank/medicine*` + `player_slot_count` | `inventory.* / bank.* / shop.* / produce.* / lootrule.*` | → battle `CombatHooksDirty`（事件）；→ external `(inventory,changed)` |
| **quest 任务** | `story`（+ 是否含 `idle` 见 T5） | `account_state.data.storiesMap/enemyTasks` | `story.*` | → item 奖励写入 `call`；→ external `(story,unlock)` |
| **character 角色** | `player`、`character`、`career` | `characters` 行；`account_state` 账号级字段；角色/职业/属性切片 | `player.* / career.*` + REST 角色 CRUD | → battle `StartSession/StopSession`；→ external 角色 DTO |
| **shared** | `modules/logic/shared`、`common/**` 纯工具、`game-core` 内核、`protocol` | 无业务状态 | 纯函数/契约 | — |

> **map / dungeon 两服是续篇 [09](09-地图与秘境逻辑服.md) 追加的结论**（已拍板**拓扑 B**）。
> 分工原则：**battle 是唯一仿真器与会话宿主，map/dungeon 是控制器（决定生命周期），character 是唯一持久化写者**。
> **09 经评估后明确不采用 ionet 的 room（房间）模型**（理由见 09 §1）：room 不是框架角色、
> 本作无多人（成员恒 1）、TS 端无 room 路由/范围投递/回收，自建成本远大于收益。
> 09 还实测出地图/秘境的一批**死机制与 bug**（无尽钥匙永不掉落、`pendingMaps` 从不写入、
> `endlessLevel` 被静默丢弃、进图与通关**双扣票**、`resetPrice/cooldown` 未实装），
> 并给出已拍板处置：**进图扣票一次（修双扣）**、**无尽暂缓登记**、
> **离线只在战斗区域结算且击杀计入任务**。

> **`game-core` 不动**：它是共享内核（数据表/规则/战斗算法）。"战斗逻辑服"指的是**宿主与路由边界**
> 在 battle，不是说 `game-core` 的代码搬走。`AGENTS.md` §4 的冻结契约继续有效。

### 2.3 解环方案（每条环 → 目标方向）

| 现状环 | 破解动作 | 目标方向 |
|---|---|---|
| `world → story` ↔ `story → world` | battle 发 `MapEntered`/`EnemyKilled` 事件，quest 订阅；quest 的当前地图改读已持久化的 `account_state.data.worldMaps[characterId].map`（`player-context.service.ts:458-466`），不再调 `WorldService.positionOf` | **battle → quest** |
| `world → inventory` ↔ `inventory → world` | `PanelCharacterService`/`notify` 上移 external/shared（纯注册表+推送）；`markCombatDirty` 改为 item 发 `CombatHooksDirty` 事件、battle 订阅 | **item → battle** |
| `career → world`（潜在） | 等级提升由 battle 发 `CareerLevelup` 事件，career/external 订阅推送；world 不再反向调 | **battle → character/external** |
| `battle → item`（掉落写背包） | 保留事件方向，**背包唯一写者归 item**；battle 只产出掉落事件/批量提交 | **battle → item**（事件，非写调用） |
| `character ↔ battle` 选角指针 | "当前角色"唯一权威放 external 会话表；battle 只订阅 `ActiveCharacterChanged`/`SessionStop` | **character → battle**（单会话）+ external 权威 |

**结论**：解环后依赖图为 DAG，且**所有跨服副作用都走事件/调用**，为将来进程拆分铺路。

## 3. 逻辑服边界怎么落成**可验收**的门禁

> 架构不能靠"约定"，必须有会失败的测试。新增：

**`packages/server/test/logic-server-boundary.test.ts`（静态扫描源码 import 图，纯确定性）**

1. 解析 `packages/server/src/**/*.ts` 的相对 import，构建图；
2. 断言**无环**（含 `world/story/inventory` 三条已知环的回归）；
3. 断言**跨逻辑服不出现深路径 import**：只允许 `<server>/logic-server.js`、`<server>/*.action.js`
   （`@ActionController` 只允许出现在自己的服里）、`shared/**`、`common/**`、
   `@idle-dark/protocol`、`@idle-dark/game-core`；
4. 断言每个 `*/logic-server.ts` 导出 `XxxLogicServer` 且**无 `@ActionMethod`**；
5. 断言 `protocol` 的每个 cmd 段（`CMD_SEGMENTS`）**恰好归属一个逻辑服**（防两服抢同一段）；
6. 边界用例：空目录、无法解析的 import、循环自引用、动态 import —— 不得静默通过。

**数字门槛**：`逻辑服间深路径 import 数 = 0`；`import 图 SCC 数 = 0`（单进程阶段用"每服一个 DAG 组件"表达）。
