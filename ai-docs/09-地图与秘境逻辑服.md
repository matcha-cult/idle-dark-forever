### 0.2 三条支撑结论（实测/权威来源）

1. **room 不是 ionet 的框架角色**：`Room/RoomService/OperationHandler` 全在 `extension-room`，
   `net-server`/`net-logic-server`/`net-center` **完全不认识 roomId**；`SimpleRoomService` 是"默认内存实现"。
   TS 端更弱：`DistributedRoom.broadcastToRoom` **全实例广播、无成员过滤**，无 room→实例路由、
   无空房回收、无崩溃恢复，`extension-nestjs` 的分布式广播通路**从未接线**。
2. **本作没有多人**：一个 `(userId, characterId)` 一棵内存 `BattleWorld`，怪物按角色实例化，
   **无跨角色共享地图态、无组队** → room 的成员/广播两项今天恒为空转。
3. **秘境现状是"死机制 + bug"**（见 §3.2）：无尽钥匙永不掉落、`pendingMaps` 从不写入、
   `endlessLevel` 被静默丢弃、**进图与通关双扣票**、`resetPrice/coolDown` 未实装、run 相位不落库。

## 1. 决策记录：为什么不用 room 模型

> 保留本节，避免后续会话重复提出 room 方案。触发重新评估的条件见 §1.3。

| # | 事实 | 来源 |
|---|---|---|
| F1 | room 是**应用模块特性**，不是服务端角色；框架不托管 room、不为 room 分配进程 | KB `stable/api-contracts/room-operation-api-contract.md`；Java `extension-room/SimpleRoomService.java`（"Default in-memory"） |
| F2 | 「每房间单线程/串行」**不是框架保证**；`room.operation(...)` 在调用线程内联执行 | Java `OperationContext.execute()`；KB `room-operation-execution-concept.md` |
| F3 | 房间广播本质是「目标 userId 集合 + 聚合投递」，且要在对外服侧按本地连接收窄 | KB `room-range-broadcast-boundary-pattern.md`；Java `DefaultRangeBroadcast` → `BroadcastUserListMessage` |
| F4 | 房间持久化/清理/崩溃恢复**框架零保证** | KB `room-operation-api-contract.md` "Do Not Infer" |
| F5 | **多实例房间归属/路由不提供**：同 cmdMerge 只保留一个 owner、注册第二个会替换、不轮询；`bindingLogicServer` 是企业功能桩且**绑 user 不绑 room** | Java `DefaultLogicServerLoadBalanced` javadoc、`DefaultFindServer` |
| F6 | TS 端 room 只能到「成员集合 + 无范围 pub/sub」 | ionet-ts 审计：`packages/redis/src/distributed-room.ts` 等 |
| F7 | 本作**无多人/组队**，房间成员恒 1 | 本仓实测（grep `party/coop/组队` 零命中） |

**结论**：在"恒 1 成员 + 无多人"下，room 换来的语义近乎空转，却要自建框架不提供的一整套机制。
→ 用普通会话对象 + 控制器承载，即可拿到同样收益（挑战生命周期、回收、per-会话调度、推送收窄），成本低一个量级。

### 1.3 何时重新考虑
出现**组队/多人同图/跨角色共享怪物**、需要**独立匹配与房间发现**的玩法，
或框架补齐**范围投递与 room→实例路由**时，重新评估。

## 4. 目标分工（拓扑 B）

### 4.1 谁拥有什么

| 逻辑服 | 拥有 | 不拥有 |
|---|---|---|
| **battle 战斗（仿真器 + 会话宿主）** | 全部 `WorldSession`/`RunSession` 的**运行时**：`BattleWorld`、units、相位机、RNG、**tick 调度**、伤害判定、经验获取、掉落**判定**、`battle.focus/snapshot` | 地图目录/解锁、票务/冷却、挑战队列决策、结算编排 |
| **map 地图（控制器）** | 开放世界：地图目录与解锁判定（`checkRequirement`）、位置解析与**世界种子**、`map.enter/leave/list/snapshot`、开放世界会话的建/切/关决策、进图剧情触发（事件） | 战斗单位、相位机、挑战队列 |
| **dungeon 秘境（控制器）** | 秘境挑战 + **挑战队列**：票校验与**唯一扣费**、**冷却/每日重置/神力重置（RC3）**、`group` 归属、**挑战队列 `ChallengeQueue` 的所有权与推进**（RC4/RD3）、相位推进**决策**、通关/死亡结算编排、`outside` 返回、**离线结算编排**（见 §6） | 战斗单位、tick、地图目录 |
| **character 角色** | `Player`/`characters.state`/`account_state` 的**唯一写者**（含 `worldMaps`/`worldSeeds`/`dungeonTickets`/冷却状态）、选角会话原子性 | 地图语义、战斗 |
| **item / quest** | 同 08 §2.2 | — |
| **external 对外服** | 握手、路由、在线集合、当前角色、推送汇聚（按本地连接收窄） | 业务 |

**为什么 battle 必须做仿真**：两边各自跑仿真会让 `BattleWorld` 生命周期与 tick 预算重复实现，
且"战斗逻辑服"名存实亡；拓扑 B 让 battle 成为唯一仿真器与 tick 宿主，
map/dungeon 只在**上线/进图/通关/死亡**等低频点跨服 → **tick 零跨进程**。

### 4.2 依赖图（方向敏感）

```
client ─▶ external ──player.select──▶ character
character ──PlayerSelected(userId,char)──▶ map                 // 解析开放世界位置
map ──StartSession(sessionId=char, spec)──▶ battle             // 命令（建会话）
client ──map.enter(mapKey)──▶ map ──SwitchMap(sessionId,mapKey,seed)──▶ battle
client ──dungeon.enter(mapKey) / dungeon.queue.set / dungeon.reset──▶ dungeon
dungeon ──CostTicket / ResetCooldown(opId)──▶ character        // call，幂等（唯一扣费/扣神力）
dungeon ──StartRun(runId, spec)──▶ battle                      // 命令
battle ──RunEnded(runId, reason=clear|death)──▶ dungeon        // 事件（反馈）
dungeon ──NextPhase(runId)|ExitToMap(returnMap)──▶ battle
dungeon ──ContinueOpenWorld(characterId, mapKey)──▶ map        // 队列耗尽后转非秘境（RD3）
battle ──EnemyKilled / MapEntered──▶ quest                     // 事件
battle ──LootLanded(batch)──▶ item                             // 事件；背包唯一写者=item
map|dungeon ──PersistPosition(characterId,{map,endlessLevel})──▶ character
character ──SessionStop(characterId)──▶ map & dungeon & battle  // 事件
battle ──(world,tick)──▶ external ─▶ 角色连接
```

### 4.3 环与破解

| 环 | 破解 |
|---|---|
| `battle ↔ dungeon` | **命令单向进入**（`dungeon --StartRun/NextPhase/ExitToMap--> battle`）+ **事件单向反馈**（`battle --RunEnded--> dungeon`）；battle 不反向 import dungeon |
| `battle ↔ map` | `map --StartSession/SwitchMap/CloseSession--> battle`；map **不订阅** battle |
| `dungeon → map`（队列耗尽转非秘境） | **单向命令**；map 不回调 dungeon → 不成环 |
| `character ↔ map/dungeon` | `worldMaps`/`worldSeeds`/tickets/冷却 **唯一写者 = character**；map/dungeon 发请求；character 不 import 它们 |
| 现有 `world ↔ story` / `world ↔ inventory` | 按 08 §2.3 解环（`MapEntered`/`EnemyKilled`、`CombatHooksDirty`、`notify`/`panel-character` 上移 external） |

**同步调用只允许两条方向**：`map|dungeon → character`（落位置/扣票/扣神力）与 `character → battle`（启停会话）；
其余全部事件 → 依赖图保持 DAG。

## 5. 会话与挑战生命周期

### 5.1 开放世界会话 `WorldSession`

```
(选角) → creating → active ⇄ switching(mapKey) → closing → destroyed
                    建会话(battle)  SwitchMap     登出/切人/握手重置/空闲超时
```
- 触发：`player.select`（建）/ `map.enter`（切图，**不重建**，只换 map+seed）/ `world.leave`・握手重置・空闲超时（关）；
- 运行时 units 不落库；位置与种子由 character 落库。

### 5.2 秘境挑战 `RunSession`

```
dungeon.enter(票校验 + 唯一扣费 + 冷却校验 + 生成 runId)
   → creating → running(phase 0..n)
        ├─ 相位清空 → dungeon 决定：同 run 下一相位 / 结算本条目 / 推进队列下一条目
        ├─ 死亡     → dungeon 结算(败) → 推进队列下一条目（当前条目作废，票不退）
        └─ 主动离开 → dungeon 结算     → 队列保留（可恢复）
   → settling(奖励/账目/报告) → destroyed
```
- **新增 `runId`/`runSeq`**：由 `dungeon.enter` 生成、随 run 落库，保证**幂等**与**重启可恢复**（修 M7）；
- **扣票只此一处**（修 M5）：内核通关扣票逻辑改为"接收已扣费规格"或移除；
- 相位推进决策从 `spawner.DungeonState.switchToPhase` **上移**到 dungeon，battle 只执行"进入下一相位"。

### 5.3 挑战队列 `ChallengeQueue`（RC4 + RD3）

- **服务端唯一所有者**：结构 = 有序条目 `{ mapKey, endlessLevel? }[]`，随角色落库（`characters.state` 或 `account_state.data` 的**单一归属**，不得两处）；
- **玩家可设定**：客户端通过 `dungeon.queue.set/add/remove/clear` 增删（**加性子协议**，不改现有 DTO 形状）；
- **推进规则**（在线与离线**共用同一实现**）：
  1. 进入队列首条目：秘境 → 校验票/冷却 → `battle.StartRun`；非秘境 → `dungeon --> map.ContinueOpenWorld`；
  2. 条目结束（通关或死亡）→ 弹出该条目 → 推进下一条目；
  3. **队列耗尽 → 自动转入非秘境战斗图**（RD3）：发 `map.ContinueOpenWorld`，
     目标图 = `run.outside` → 角色持久化的开放世界位置 → `home`（**待确认，§10 RD4**）；
  4. 秘境条目**无票/冷却未就绪** → 跳过该条并记录（**待确认，§10 RD5**），不中断整个队列。
- **与原版差异**：原版队列由**前端** `MapPanel` 维护、离开即清空；本设计改为**服务端权威 + 落库**，
  客户端刷新/重登/离线都不丢队列。

### 5.4 冷却 / 每日重置 / 神力重置（RC3）

- **字段语义**（对齐数据表）：
  - `coolDown`：冷却时长（样本 86400000ms = 24h）；`coolDownOffset`：重置偏移（决定"每日 4 点"的基准）；
  - `maxCoolDownStack`：可累积的冷却层数（每层 = 一次可挑战机会）；
  - `resetPrice`：用**神力**重置冷却/购票的价格；`-1` = **不可重置**（实测 `silver.warrior`）；
  - `defaultTicketCount`：初始票数（实测 47 图全 `undefined` → 现行为 `?? 1`）。
- **状态形状**（per character，per ticketKey=`group ?? mapKey`）：`{ stacks, lastResetAt, lastUsedAt }`；
  与 `dungeonTickets` 同处 `characters.state`（**单一写者 = character**）。
- **每日 4 点重置**：必须用注入的 `GAME_CLOCK`（`AGENTS.md` §1.5 **禁裸 `Date.now()`**）；
  时区与偏移由 `coolDownOffset` + 显式配置决定（**待确认，§10 RD6**）。
- **边界**：`resetPrice` 为 `undefined` / `0` / 负数（-1 不可重置）/ 超大；`coolDown` 为 `0`/缺失/负数；
  `maxCoolDownStack` 为 `0`/缺失/超大；神力不足；重复点击（`opId` 幂等）。
- **协议**：新增 `dungeon.reset`（神力重置/购票）、`dungeon.queue.*`（子命令），旧字段不变（加性）。

## 6. 离线结算规则（RD1 / RD2 / RD3）

### 6.1 战斗区域判定（唯一定义）

```
isCombatArea(map): boolean
  = map != null && (map.isDungeon === true || (map.monsters?.length ?? 0) > 0)
```
- 边界：`map` 为 `undefined/null`、`monsters` 缺失/空数组、`isDungeon` 非布尔、未知 mapKey → **false**；
- 定义放 `game-core`（纯函数，可单测），map/dungeon/quest 共用，**禁止各处复制**（对齐 `AGENTS.md` §11 纪律）。

### 6.2 离线结算流程（秘境必须支持）

```
离线 → 取当前状态：位置 {map,endlessLevel} + 挑战队列（由 dungeon 控制器提供规格）
     → 按队列顺序逐条目在"虚拟时钟"上模拟（与在线共用同一套推进决策）
        · 秘境条目：相位推进 / 通关 / 死亡 全部走 dungeon 的决策纯函数
        · 非秘境条目：开放世界战斗模拟
        · 预算耗尽即停（见 §6.3）
     → 产出 report：经验/金币/掉落/**击杀**/**队列推进结果**
     → report 缓存（现有 IdleService.cached，保证 report/claim 一次）
     → claim 时落地：
         · 经验/金币/掉落 → character/item（写）
         · 击杀 → quest（**恰好一次**，RD2）
         · 队列/位置/票账 → character（写）
```

### 6.3 关键约束

- **在线/离线共用推进决策**：秘境相位、通关/死亡、队列推进必须是**同一份纯函数实现**
  （dungeon 控制器持有），在线用真实 tick、离线用虚拟时钟；**禁止两套逻辑**（否则必然漂移）。
- **时间预算与"跨秘境外推"**：现有 `IdleService` 是 30 分钟模拟 + 速率外推。
  队列化后必须明确：预算内**按条目顺序**模拟；**预算耗尽即停在当前条目**；
  **不允许**对秘境做速率外推（会把"打不过"直接推成"通关"）。
  外推只允许发生在**最终稳定在非秘境战斗图**时（**待确认，§10 RD7**）。
- **离线击杀计入任务（RD2）**：与在线不重复计数（在线由 battle 发、离线由 idle 发，quest 是唯一写者）。
- **幂等**：报告缓存 + `opId`；重复 `claim` 不得二次递减任务、不得二次推进队列。
- **安全区不结算（RD1）**：队列为空且当前图非战斗区域 → `zeroReport`。
- **归属修订**：`idle`（离线结算编排）**归属 dungeon 控制器**（因为它必须推进挑战队列），
  **不再放 battle**（修正 08 §6 B2 的建议）；仿真内核仍是共享 `game-core`。

### 6.4 无尽（暂缓）

- 本轮不实装也不删除；死路径登记在 M1/M3/M4；
- **dungeon 控制器不得依赖无尽链**（不得假设 `endlessLevel>0`、不得假设钥匙会掉）。

## 8. 门禁（在 08 §5 基础上追加）

1. `logic-server-boundary.test.ts`：无环；`map/dungeon/battle` 之间**只允许** §4.2 的方向（含 `dungeon → map`），
   出现反向 import 即失败。
2. **扣票不变量**：`dungeon_ticket_charged_total == dungeon_run_total`（修 M5 的回归门禁）。
3. **run + 队列可恢复**：重启后 `{map,endlessLevel,runId,queue}` 可从 DB 恢复（修 M7/M2）。
4. **队列唯一所有者**：同时只允许一处实现队列读写；客户端不得直接改服务端队列状态。
5. **在线/离线推进一致**：同一初始状态下，在线推进与离线推进的**决策结果一致**（用同一批纯函数单测对拍）。
6. **离线幂等**：同 report 的任务递减次数 = 1、队列推进次数 = 1；安全区 offline 无任何奖励。
7. **推送范围**：非目标角色的连接收到 `(world,tick)` 帧数 = 0（沿用 `AGENTS.md` §15）。
8. **`isCombatArea` 唯一定义**：全仓只有一处实现。
