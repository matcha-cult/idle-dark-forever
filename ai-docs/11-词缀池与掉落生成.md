# 词缀池与掉落生成（代码实测清单）

> ⚠️ **2026-09 重构后已部分失效（见 `12-装备与伤害体系重构任务书.md` / `AGENTS.md` §18）**：
> - 装备词缀 **27 → 26 条**（删 `sta`）；**新增 `affixType`（前缀/后缀）+ `tag` 预分类**；
> - 条数规则改为「普通 1+1 / 优秀 3+3 / 传奇 3+3 + 1 传奇」的**前后缀分池**，不再是「条数 = 品质」；
> - `Quality` 由 7 档压到 **3 档**（0 普通 / 1 优秀 / 2 传奇），`BASE_QUALITY_RATE` 压到 4 项；
> - `darkResist/darkAbsorb` 词缀改名为 `chaosResist/chaosAbsorb`（混沌非元素）；
> - **装备掉落已全部摘除**（184 条 equip 条目，P11），本文件 §2 的池子仍适用于 0 级城镇商店产出的底材。
>

> 用途：把**当前实现里真实存在的词缀池**固定下来，供策划核对数值、供后续写测试与回归。
> 所有 key / 文案 / 公式 / 部位限制都**逐字取自源码**，不是凭记忆或原版印象。

>

## 0. 一句话结论

**三张池子，只有装备词缀是"掉落时随机抽"的：**

1. **装备词缀** 27 条（`data/affixes.ts`），按**物品的 `position` / `class` / 等级**过滤后加权抽取，
   每件装备的条数**等于品质**（0~4 条），同一件内不重复；
2. **敌人词缀** 3 条（`data/enemy-affixes.ts`）**不是随机池** —— 它只是 hook 定义，
   具体某只怪带哪几条由该怪自己的 `enemyData.affixes` 权重表和 `quality` 决定，且**允许重复**；
3. **传世/传说** 24 条（`legends.ts` 16 + `packages/year2018.ts` 8），走 `generateEquip` 的
   `legendType` 参数，**固定追加在最后一条**，不参与加权抽取；`quality === 4` 才可能掷出，
   且随机掷的那 16 条**排除 `special: true`**（8 条年兽套只能由掉落表直给）。

`data/packages/*` **没有**增删改任何 `affixes` / `enemyAffixes`（`grep` 0 命中），所以装备/敌人词缀池
= 基础表原样。

## 3. 敌人词缀池（3 / 3）

定义于 `data/enemy-affixes.ts:20-45`。hook 签名是 `(world, value) => newValue`，`this` = 敌人单位
（`_shapes.ts:268-275`、`contracts/data.ts:107-112`）。

| # | key | name | hooks | 效果 |
|---|---|---|---|---|
| 1 | `stronger` | 强壮的 | `maxHpMul: (world, value) => value * 1.5`；`atkMul: (world, value) => value * 1.5` | 最大生命 ×1.5、攻击 ×1.5 |
| 2 | `faster` | 快速的 | `atkSpeedMul: (world, value) => value * 2` | 攻速 ×2 |
| 3 | `recover` | 自愈的 | `hpRecovery(world, value) { return value + this.maxHp * 0.005; }` | 回血 + 最大生命 ×0.005 |

**挂到怪物身上的方式**（`combat/enemy-unit.ts:54-106`）：

1. 构造器接收 `quality`（`EnemyUnit(world, type, quality = 0, savedState)`）；
2. 若有存档且 `savedState.affixes.length === quality` → 直接恢复 `this.affixes`（`:67-68`）；
3. 否则循环 `quality` 次，从**该敌人数据自身的** `enemyData.affixes`（`Record<string, number>` 权重表，
   `contracts/data.ts:130`）按权重加权抽取，随机源 `this.world.rng.affix.next()`（`:70-84`）；
   **没有去重 / blacklist**，同一 key 可被重复抽中；权重和为 0 时回退 `keys[0]`；
4. 每条抽中的词缀遍历 `hooks`，用 `this.addAttrHook(key, hooks[key]!.bind(this, this.world))` 注册（`:96-106`）；
5. 展示名 `this.affixes.map(v => tables.enemyAffixes[v]?.name ?? v)`（`:228`）；序列化 `ret.affixes = this.affixes.slice()`（`:478`）。

> 结论：本文件**不含**任何部位/职业/等级限制字段；「某只怪带几条、带哪些」完全由怪的
> `enemyData.affixes` 与 `quality` 决定。这与装备侧"从全局池里抽"是两种模型，做数值时别混。

## 4. 传世 / 传说词缀（24 / 24）

### 4.1 与普通词缀池的关系

- **不是同一张表，但共用实例类型**：`rules/inventory-slot.ts#AffixInfo.affixData` 先查 `tables.affixes`、
  再查 `tables.legends`（`:122-128`）；`isLegend` 的判据是 `!!tables.legends[key]`（`:130-132`）。
- **走 `generateEquip` 的 `legendType` 参数**（`rules/goods.ts:131-168`）：普通词缀条数
  `= legendType ? quality - 1 : quality`；传奇**无条件追加在数组末尾**（`:145-158`）。
- `randomEquip` **只在 `quality === 4`** 时才可能附传奇（`:187-210`），且挑选时**排除 `special: true`**（`:195`）。
- `specialEquip` 掉落绕过 `randomEquip`，直接 `generateEquip(legend.type, eLevel, 4, legendType)`
  （`battle-world.ts:709-722`）。
- 掷传奇概率 `specialLegendRate(tables) = 非special的legends条数 / 100`（`:122-124`）：
  本仓 24 条里 8 条 `special`（全在 `year2018`）⇒ **16/100 = 0.16**。
  原版 `__DEV__`（开发态 100%）分支**明确未移植**（`:117-121`）。

## 5. 生成与筛选规则

### 5.1 部位 / 职业 / 等级过滤

唯一真相是纯函数 `isValidAffix(tables, key, affix, level)`（`rules/goods.ts:92-114`），判定顺序：

1. `goodData` / `affixData` 任一缺失 → `false`（原版会 TypeError，这里显式拒绝，`:95-98`）；
2. `affixData.maxLevel && level > maxLevel` → `false`（`:100-102`）；
3. `affixData.minLevel && level < minLevel` → `false`（`:103-105`）；
4. `affixData.validClasses && validClasses.indexOf(goodData.class ?? '') === -1` → `false`（`:106-108`）；
5. `affixData.validPositions && validPositions.indexOf(goodData.position ?? '') === -1` → `false`（`:109-111`）；
6. 否则 `true`。

> ⚠️ 第 4 步比的是**物品的 `class`**（`sword`/`dagger`/`cloth`/`wand`/`ornament`…），
> **不是职业 key**。数据里叫 `validClasses`，很容易误读成"限定职业"。

`generateEquip` 用它构建候选池：`Object.keys(tables.affixes).filter(k => isValidAffix(tables, k, affixes[k], level))`
（`:139-141`）。**它不检查物品自身的 `minLevel`/`maxLevel`** —— 那是 `randomEquip` 挑基底时的职责（`:213-223`）。

### 5.2 品质 → 词缀条数

- 品质骰：`dice = rng.next() / mfRate`，`quality = Math.max(0, BASE_QUALITY_RATE.findIndex(v => v < dice) - 1)`
  （`:182-183`），`BASE_QUALITY_RATE = [1, 0.5, 0.05, 0.005, 0.0005, 0]`（`:22`）。

| `dice` 区间 | quality |
|---|---|
| `[0, 0.0005)` | 4 |
| `[0.0005, 0.005)` | 3 |
| `[0.005, 0.05)` | 2 |
| `[0.05, 0.5)` | 1 |
| `[0.5, ∞)`（含 `dice === 0` 的退化分支） | 0 |

- 条数 `count = legendType ? quality - 1 : quality`（`:145`）：
  **普通装备 = quality（0~4 条）**；**传奇 = 3 条普通 + 末尾 1 条传奇 = 共 4 条**（`:146-158`）。
- 负数 quality 不产出词缀（`goods.test.ts:174-177`）。
- 品质还会放大 mf：`battle-world.loots()` 里 `qualityRate = 1 << quality`，
  传给 `randomEquip(eLevel, mfRate * mf * qualityRate, position)`（`battle-world.ts:646,725`）。

### 5.3 抽取顺序与去重

1. `generateEquip` 内建 `blacklist: Record<string, boolean> = {}`（`:144`），循环 `count` 次（`:146-148`）；
2. 每次调 `randomAffixes(tables, validAffixes, level || 0, blacklist, rng)`（`:147`）；
3. `randomAffixes` 先 `config.filter(key => !blacklist[key])`（`:60`），再按 `weight || 1` 加权（`:61-70`），
   抽中后写 `blacklist[result] = true`（`:78`）⇒ **同一件装备内不重复**；不同装备之间独立；
4. 传奇不参与加权抽取，循环结束后**无条件追加**（`:150-158`）;
5. 异常路径：候选池为空、或全部候选权重 ≤ 0 → 抛
   `randomAffixes: no affix selected (empty pool or non-positive weights)`（`:72-76`，测试 `goods.test.ts:111-113`）；
   无可用基底 → 抛 `randomEquip: no valid equip base for the given level/position`（`:225-228`）。

### 5.4 等级如何进入公式

`generate(level, rng)` 的 `level` 是**装备等级**（`eLevel`），不是角色等级。计算链（`battle-world.ts:698-725`）：

1. `loots(..., level, ...)` 的 `level`：敌人死亡时 = 敌人等级（`enemy-unit.ts:441`）；副本通关 = `mapData.level`（`spawner.ts:302,307`）；
2. 无尽层加成：`if (endlessLevel) level += 35 * (endlessLevel - 1)`（`:652-654`）；
3. `minLevel = Math.max(1, Math.min(level - 15, level * 0.8))`（`:705`）；
4. `eLevel = Math.ceil(minLevel + rng.loot.next() * (level - minLevel))`（`:706`）；
5. `specialEquip` 覆盖为 `eLevel = untransformEquipLevel(player.level)`（角色等级换算，`:710`）；
6. `randomEquip(eLevel, ...)`（`:725`）→ `RulesLootService.randomEquip` 再做
   `safeLevel = Math.max(1, Math.trunc(finite(level, 1)))`（`server/.../shared/loot-service.ts:38-40`）。

同一个 `level` 同时用于：词缀数值 `generate(eLevel, rng)`、词缀资格 `isValidAffix`、
基底/传奇资格（`(good.minLevel || 0) <= level && (good.maxLevel || level) >= level`，`:218-222`）。

### 5.5 随机源（哪条 `Rng` 流）

| 用途 | 流 |
|---|---|
| 品质骰 → 传奇骰 → 传奇挑选 → 基底挑选 → 每条词缀加权抽取与数值 | **独立派生流 `equipLoot`**（`headless.ts:57-62` 的 `root.fork('equipLoot')`，经 `RulesLootService` 透传） |
| 掉落条数计数、`eLevel` 抽样、`specialEquip` 的 items 挑选 | `BattleWorld.rng.loot`（`:674,706,712`） |
| 敌人词缀抽取 | `BattleWorld.rng.affix`（`enemy-unit.ts:74`） |
| 传奇 hook 内随机（如 `mithrilRing-1` 的 `holyCombo`） | `world.rng.skill`（`legends.ts:87`） |

战斗世界构造时从根 `Rng` fork 出 9 条稳定标签流：
`target / crit / dodge / stun / break / affix / spawn / loot / skill`（`battle-world.ts:245-256`）。
**掉落与战斗判定互不扰动**，这是金样回归可复现的前提（AGENTS §1.5）。

## 8. 未核实 / 待确认

1. **装备基底的实际 `class` / `position` 取值全集**未逐条核对（词缀侧的限制值是从 `affixes.ts` 逐字读的）。
   要判断"某条词缀实际能出现在哪些装备上"，还需读 `data/goods.ts` 并做一次交集统计。
2. **`enemyData.affixes` 权重表的实际分布**（哪些怪带哪几条、权重多少）散在 `data/enemies.ts` 与
   `packages/*` 里，**未做全量统计**，本文件只核到加载/施加机制。
3. **`EnemyEntry` 视图类型未显式声明 `affixes`**，运行期靠 `Loose<T>` 的索引签名兜住
   （`_shapes.ts:342-359`）。按 AGENTS §17 的编译期门禁思路，这算一处**可能的小缺口**——
   因为 `Loose` 让 `tsc` 放行了任意字段。建议后续核实是否要显式声明。
4. **`range` 与冻结契约的偏差**：`contracts/data.ts` 把 `range` 标为 `[number, number]`，
   实际 27 条全部返回**字符串**（如 `${level+1}~${3*level+1}`）。已确认返回值形态，
   但**没有**排查是否有下游按 `[number, number]` 消费它。
5. **是否存在其它模块直接调 `generateEquip(..., legend)`**：只确认了
   `server/.../shared/loot-service.ts` 与 `server/.../inventory/internal/loots.ts:125` 两个调用点，
   未做全仓核实。
6. 24 条传说的 `special` 标志已逐条读过（基础 16 条均无、year2018 的 8 条均有），
   由此得出的 `specialLegendRate = 0.16` 是**算术推论**，非代码常量。
