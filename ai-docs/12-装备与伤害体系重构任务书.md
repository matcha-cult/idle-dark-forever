## 0. 一句话结论与三条不变式

**这次改动会同时打破三样"原本当作常量"的东西**：装备槽位集合（4 → 9）、品质档位
（**7 档 → 3 档**，且定义在冻结契约里）、角色四维（4 → 3）。

施工前必须确认的三条不变式（违反即返工）：

- **I1 存档可迁移**：`characters.state`(jsonb) 里已经存在玩家数据。**任何**槽位/属性/品质的
  结构变更都必须给出「老存档读进来会怎样」的答案，不允许静默丢装备或丢属性。
- **I2 冻结契约只许加可选字段**（AGENTS §4）：`packages/protocol/src/**`、
  `contracts/ports.ts`、`contracts/data.ts`、`game-core/src/index.ts`。本任务**必须**改
  `protocol` 的 `Quality`（7→3）与若干 DTO —— 属**破坏性**变更，需用户显式批准，
  并同步 `ui-kit` 的镜像文案与门禁测试（见 §3.4）。
- **I3 词缀生成的唯一真相只有一处**：`rules/goods.ts`。前后缀/tag 逻辑必须加在
  `isValidAffix` / `randomAffixes` / `generateEquip` 里，**禁止**在服务端或前端复制筛选逻辑
  （AGENTS §11 的教训：两处实现漂移导致面板设置静默失效）。

## 1. 七条设定的逐条解读（含现状对照与"会踩到的坑"）

### R1 装备位扩充为 9 槽

**[设定]** 主手（武器）、副手（武器）、胸甲、手套、腰带、鞋子、项链（饰品）、戒指 ×2。

**[现状]**
- 部位类型是**硬编码 4 元联合**：`EquipPosition = 'weapon' | 'plastron' | 'gaiter' | 'ornament'`
  （`packages/game-core/src/combat/player-unit.ts:33`）。
- 中文名映射在 `packages/game-core/src/rules/inventory-slot.ts:88-91`：`plastron='胸衣'`、
  `gaiter='护腿'`、`ornament='饰品'`。
- 装备底子共 **59 件**，按部位分布：`weapon` 33 / `plastron` 10 / `gaiter` 9 / `ornament` 7
  （`packages/game-core/src/data/goods.ts`，统计命令见 §9）。
- 存档键就是部位名：`PlayerLike.equipments: Record<EquipPosition, EquipmentSlotLike>`
  （`player-unit.ts:76`），序列化在 `player-unit.ts:223` 附近**遍历四个部位**。

**[坑/待定]**
1. **5 个新部位（手套/腰带/戒指×2）现在完全没有底子数据**，等于要从零设计一批装备底子；
   而现有 59 件要**重新分槽**（`weapon` 33 件要拆到主手/副手；`gaiter`/`ornament` 要重新定义）。
2. **老存档映射**：`weapon/plastron/gaiter/ornament` → 新 9 槽怎么对应？不映射就丢装备。
3. 内核里有**按槽位硬编码的特殊分支**，例如 `maxHp` 直接读 `equipments.ornament.maxHp`、
   `mpRecovery` 直接读 `equipments.weapon.mpRecovery`（`player-unit.ts:348-395`）。
   扩槽后这些"某槽专属加成"要么泛化、要么逐槽重写。
4. 用户只写了"戒指 ×2"，未说**两个独立槽**还是**一槽两枚**；也未说**要不要双手武器**。

### R2 怪物不再掉落装备，装备底子改为商店兑换

**[设定]** 怪物掉落池移除装备；装备底子由商店兑换获得。

**[现状]** 掉落链路、掉落表里产生装备的条目数量、商店实现 —— 见 §3.2（由子会话盘查后补全）。

**[坑/待定]**
1. 拾取规则（`lootRule`，AGENTS §11）里有大量**面向装备**的维度（按 `class`+`quality` 设
   拾取/出售/分解）。装备不掉落后，这部分会**退化成死代码**，需要决定：保留、收缩到材料/通货、
   还是删除（删除会动 protocol 与老存档里的 lootRule 键）。
2. "底子"是否等于**无词缀的普通稀有度装备**？这条要与 R7 一起定义。

### R3 新增 12 种通货 + 12 种精华（占位）

**[设定]** 怪物掉落池新增 12 通货 + 12 精华；**本阶段不取具体名字、不动能力设定**，
用**预占位**模式。

**[现状]** 可堆叠物品/物品定义/掉落接入点的承载机制 —— 见 §3.4（子会话盘查后补全）。

**[坑/待定]** 需要确认「占位」是否真的可行：如果物品必须写 `use`/能力函数才能登记，
那就不能纯占位。**这是本任务能否"省力"的关键**，见 §3.4 的结论。

### R4 三维：力量 / 敏捷 / 智慧，移除耐力

**[设定]** 属性改为力量、敏捷、智慧；**删除**耐力（`sta`）。

**[现状]**
- 四维定义：`str / dex / int / sta`，来源是 `roleData.attrBase` + `careerData.attrGrow × 等级`
  （`player-unit.ts:323-346`）。
- **`maxHp` 依赖 `sta`**：`ret *= this.sta / 100 + 1`（`player-unit.ts:357`）。
- 词缀池第 15 条就是 `sta`（`data/affixes.ts`）。

**[坑/待定]**
1. **硬阻塞**：删掉 `sta` 后 `maxHp` 由什么决定？现状是
   `(50 + level*10 + 饰品) × hooks × (1 + sta/100)`。必须给出替代公式
   （等级曲线？改由力量？还是纯装备驱动？）。
2. `careers.ts` / `roles.ts` 里每个职业的 `attrBase`/`attrGrow` 都带 `sta`，要改数据。
3. ~~老存档里的 `sta` 怎么处理~~ → **实测：属性根本不进存档**（见 §3.3），此坑不存在。
4. ~~装备的属性需求是否用到 `sta`~~ → **实测：不存在属性需求**，装备门槛只有等级。
5. 🔴 **真正的风险**：词缀按 key 持久化，而 `rebuildEquipmentHooks` 读 `affixData.hooks`
   **没有判空** ⇒ 删掉词缀 `'sta'` 后，老存档里带该词缀的装备**载入即抛 TypeError**。
   **删任何词缀 key 之前必须先修这个判空**（详见 §3.3 的红框与 §4 E1）。

### R5 攻击 / 施法两种基础伤害 + 元素体系

**[设定]**
- **攻击**直接造成**物理**伤害；武器还可**附加元素伤害**。
- **施法**造成**法术**伤害；法术可造成**物理**伤害，或**单一**元素伤害；法术也**可附加元素伤害**。
- 元素 = **冰霜 / 火焰 / 闪电**；**混沌**不算元素（视为无属性）。
- 物理→闪电、冰霜→火焰的**转换本期不实装**。

**[现状]** 伤害类型取值集合、抗性/吸收结算链、`isAttack`、`dark` 的定位 —— 见 §3.3。

**[坑/待定]**
1. **"附加伤害"的结算语义**必须拍板：基础伤害与附加元素伤害是**分别过各自抗性/吸收再相加**，
   还是**合并后按基础类型结算**？前者是 ARPG 通行做法，但要改 `sendDamage`。
2. 现有"物理伤害"用的是哪个 damageType？（大概率是 `melee`，需确认）是否要新增 `physical`。
3. `dark`（暗影）现在在抗性/吸收体系里有一整套（`darkResist`/`darkAbsorb`）。用户说混沌
   "不算元素、视为无属性" —— 那 `dark` 是保留为独立类型、还是就是混沌？
4. 转换"本期不实装"：**数据结构要不要预留**（预留则以后加逻辑即可，不预留则以后要改存档）。

### R6 词缀加 tag，且同一 tag 只能在前缀或后缀之一 roll 出

**[设定]** 每条词缀有一个 tag；tag 决定它属于**前缀**还是**后缀**。例：生命值/生命回复 →
前缀；抗性 → 后缀。

**[现状]** 词缀池 27 条，字段为
`key/display/validPositions/validClasses/generate/range/hooks/weight/minLevel/maxLevel`
（`data/affixes.ts`）——**当前没有任何 prefix/suffix/tag 概念**（待 §3.1 复核确认）。

**[坑/待定]**
1. **27 条要逐条打 tag + 定前后缀**，这是一份需要用户 review 的**数据设计**产物。
   建议由实施会话按语义拟一版表（本文档 §3.1 会给建议，但**不实装**），用户过一遍再落地。
2. "tag 只能在前缀或后缀中 roll 出"的**准确含义**：是「tag → 前缀/后缀」的固定映射
   （同一 tag 不会两边都有），还是「同一件装备里同一 tag 不能重复出现」？按字面是前者。
3. **传奇词缀是否豁免**该规则？（建议豁免：传奇是手写的特殊词缀，不参与前缀/后缀抽取）

### R7 稀有度三档 + 词缀数目

**[设定]**
- 稀有度：**普通 / 优秀 / 传奇**。
- 普通 = **1 前缀 + 1 后缀**；优秀 = **3 前缀 + 3 后缀**；传奇 = **词缀数量不限，每条都特殊**。
- 普通、优秀**可以手工制作**。

**[现状]**
- 品质是**7 档**：`protocol/src/dto.ts:13` 的 `Quality = 0|1|2|3|4|5|6`，文案
  `普通/优秀/精良/史诗/传说/远古/神器`（`ui-kit/src/game/quality.ts`，并由
  `ui-kit` 的 `hygiene.test.ts` 与 protocol 做一致性断言）。
- 品质骰 `BASE_QUALITY_RATE = [1, 0.5, 0.05, 0.005, 0.0005, 0]`（`rules/goods.ts:22`），
  **词缀条数 = quality**（`:145`）。
- 拾取规则的键是 `c:{class}:{quality}`，`LOOT_RULE_MAX_QUALITY = 6`（`rules/loot-rule.ts:46`）。

**[坑/待定]**
1. **这是破坏性契约变更**：`Quality` 从 7 档压到 3 档，会同时动
   `protocol`、`ui-kit`（文案 + 门禁测试）、`rules/loot-rule.ts` 的键空间、
   以及**玩家已保存的 lootRule 设置**（quality 3..6 的键会失效）。
   两条路线必须选一条：**(a) 改类型为 `0|1|2`**（干净，破坏性，需迁移）；
   **(b) 类型保留 `0..6`、语义只用 `0/1/2`**（不破坏协议，但留下 4 个死档位，容易误用）。
   **建议 (a)**，理由：留死档位迟早会在别处被 roll 出来（`BASE_QUALITY_RATE` 就是按长度骰的）。
2. 词缀条数从"= quality"改成"普通 1+1 / 优秀 3+3"是**前后缀分池**的产物，
   `generateEquip` 的算法要重写（现在是单一 blacklist 池里抽 N 次）。
3. **"手工制作"现有基础是什么**（是否已有 `produce` 域可扩展），见 §3.2。
   还要定义：制作**消耗什么**（通货/精华/金币）、**产出什么稀有度**、**词缀是否随机**。
   注意用户明确要求本阶段**不要在通货能力上投入精力** —— 因此制作系统建议**只做骨架**，
   配方与消耗后置（见 §4 批次 D）。

**数据面**

- **`ornament` 现在同时承担「项链 + 戒指」**：7 件里 `copperRing`/`ironRing`/`mithrilRing` 是戒指语义，

⇒ **只要 `EQUIP_SLOTS` 改对，服务端面板槽位这一层自动覆盖。**

- `CareerInfo.fromJSON` 遍历 `EQUIP_SLOTS` 并对缺键回落空槽（`career-info.ts:88-93`）⇒ **老存档读进来不会崩**，新槽为空。
