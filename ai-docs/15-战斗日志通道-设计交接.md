## 1. 问题

**战斗日志当前搭在 `(world, tick)` 上一起下发，而不是走独立的 `battle.log` 推送路由。**
需要评估是否/如何改成独立通道，以及事件的粒度、频率、上限、观测与断线补偿。

## 2. 现状实测（唯一真相，先信代码）

### 2.1 日志的**唯一实际通道**：`(world, tick)` = **cmd 30 / subCmd 5**

| 项 | 值 |
|---|---|
| 常量 | `WORLD_CMD.tick`（`packages/protocol/src/cmd.ts`；`CMD_SEGMENTS.world = 30`） |
| 载荷 | `WorldTickDto`（`packages/protocol/src/dto.ts`） |
| 事件类型 | `BattleEventDto` = `damage / heal / dodge / death / buff / exp / general` |
| 服务端发送 | `packages/server/src/modules/logic/world/world.service.ts#emitTick()`（约 380–409 行） |
| 频率 | `WORLD_CONFIG.tickIntervalMs = 200ms`（5Hz/连接，AGENTS §14） |
| 批处理 | `NotificationBatcher`（`packages/server/src/modules/game/notification-batcher.ts`） |
| 合并策略 | `registerMerger(WORLD_CMD.cmd, WORLD_CMD.tick, mergeWorldTick)`（`world.service.ts:174`） |
| 合并语义 | `mergeWorldTick`：`serverTime` 取 max、`units` 取**最新帧**、`events` **拼接**、`gainedExp/Gold` 相加、`wave` 取最新（`world.service.ts` 文件尾部） |
| 前端消费 | `packages/web/src/stores/world-store.ts#handleNotification`：`cmd===30 && subCmd===5` → `appendEvents(this.log, tick.events, tick.serverTime, …)` |

`WorldTickDto` 形状（含 W11 新增字段）：

```
{ serverTime, units: UnitStateDto[], events: BattleEventDto[],
  gainedExp, gainedGold, wave?, bossEvery? }
```

⚠️ `units` 是**整份单位快照**（不是增量），所以 tick 帧大小主要由 `units` 决定，日志只占其中一部分。

### 2.2 `battle.log`（cmd 40 / subCmd 1）是**已声明但服务端从不发送**的死通道

- `packages/protocol/src/cmd.ts` 的 `BATTLE_CMD = { cmd: 40, log: 1, loot: 2, focus: 3 }`。
- `packages/server/src/modules/logic/battle/battle.action.ts` 顶部注释明确：
  「本波只落地 `battle.focus`。`battle.log` / `battle.loot` 是**推送路由**（`world.tick` 与掉落记录已经承担），不注册请求 Action」。
- 全仓 `grep BATTLE_CMD.log` 只命中**前端处理分支**（`world-store.ts:261`），**服务端零发送点**。
- 因此：**改造成本低** —— 路由常量、DTO 位、前端分支都已存在，缺的只是服务端 `enqueue` 与合并策略。

### 2.3 同段真正在推的是 `battle.loot`（40/2）

`emitTick` 在发完 tick 后，把 `session.pendingLoot` 逐条 `enqueue(BATTLE_CMD.cmd, BATTLE_CMD.loot, LootDto)`；
前端弹「获得战利品 / 自动出售 / 自动分解 / 包裹已满」。`registerMerger(BATTLE_CMD.loot, mergeLoot)`。

### 2.4 事件从哪来

`game-core/src/combat/battle-collector.ts#BattleCollector`（实现 `BattleSink`）把内核事件收集成
`events` + 累计量（`gainedExp`/`gainedGold`/`kills`/`loots`/`materials`）；`WorldService` 在 tick 里
`session.collector.drain()` 取出本帧事件。离线结算用同一个 `BattleCollector` 生成 `OfflineReportDto`
（**离线不走推送**，走 `idle.report/claim` 拉取）。

### 2.5 推送防线参数（设计必须考虑的硬约束）

`NotificationBatcher`（`notification-batcher.ts`）：

| 参数 | 默认 | 语义 |
|---|---|---|
| `flushIntervalMs` | 200 | 定时 flush 周期（≈5Hz/用户，与 tick 同频） |
| `maxRoutesPerUser` | 32 | **单用户待发路由数上限**；超过则**新帧被真正丢弃**并累计 overflow |
| 合并粒度 | `(userId, cmdMerge)` | 同路由一个批次只留一帧，`data` 走注册的 merger（默认后者覆盖） |
| 丢帧后果 | `meta.resync=true` + `dropped` | 调用方应补推全量快照；`provider` 里默认只 `console.warn` |
| 指标 | `batcher.stats` = `flushed/dropped/resyncs/pendingUsers/pendingFrames/pendingOverflow` | ⚠️ **当前没有接到 `/api/metrics`**（见 §4 观测缺口） |

⚠️ 关键：**`battle.log` 若新增为独立路由，会占用 `maxRoutesPerUser` 的一个名额**（目前 world.tick 1 + battle.loot 1，共 2 个，远未到 32，无风险）。

## 3. 为什么可能值得改（设计动机，仅供权衡）

1. **耦合**：日志与整份 `units` 快照同帧同路由 → 只想刷日志时也必须带快照；想降频/丢日志时会连快照一起动。
2. **频率**：日志想更细（战斗瞬间）或更疏（例如 1Hz 汇总），都会被 tick 的 5Hz 绑住。
3. **过滤/频道**：将来做「只看我的伤害 / 只看暴击 / 只看 BOSS / 分频道」需要独立通道；现在过滤要在服务端从 tick 里拆，或在客户端丢。
4. **体积**：`events` 是逐条伤害事件，量可很大；与快照放同一帧会直接推高每帧 payload。
5. **丢帧语义**：`mergeWorldTick` 把同批事件拼接（不丢日志），但**路由超限丢的是整帧**（日志+快照一起丢），与「日志可丢、快照必须准」的目标不一致。
6. **观测缺口**：batcher 的 `dropped/resyncs/pendingFrames` **没有暴露到 `/api/metrics`**，违反容量不变式 I5「每个限额都要能看到当前值」。

## 4. 选项空间（A–E，含影响面）

> 编号非优先级；请结合 §6 决策清单拍板。

### A. 维持现状（日志继续走 `world.tick`）
- 影响面：0。
- 代价：§3 的耦合/频率/体积/丢帧语义问题不解决。
- 适合：日志量与频率都在可接受范围、暂无频道化需求。

### B. 日志独立走 `battle.log`(40/1)，tick 不再带 `events`
- 服务端：`emitTick` 把事件改为 `enqueue(BATTLE_CMD.cmd, BATTLE_CMD.log, { serverTime, events })`；为 `battle.log` 注册 merger（建议「拼接 events + 取最新 serverTime + 事件条数上限」）。
- 协议：`WorldTickDto.events` 若**删除**属于契约破坏（AGENTS §4 冻结契约「只许加可选字段」）——需要显式批准；**更稳妥**是保留字段但服务端不再填充（前端兼容处理空数组），或走废弃流程。
- 前端：`world-store.ts` 已有 `(battle, log)` 分支（现成），只需确认 `appendEvents` 的 `serverTime` 回退（`payload?.serverTime ?? Date.now()` 里 `Date.now()` 是否可接受，前端允许）。
- 风险：断线重连时 `battle.log` 的批内合并与 `resync` 语义要一起定义；离线报告不受影响。

### C. 双通道分流：低频/关键事件留 tick，高频伤害走 `battle.log`
- 例如 `death/general/buff/exp` 留 tick，`damage/heal/dodge` 走 log。
- 好处：关键叙事与快照同帧（顺序天然一致），高频噪声独立。
- 代价：**顺序/因果在前端需要跨两条消息重排**（`serverTime` 相同、帧到达顺序不保证）——要定义前端合并规则。

### D. 聚合/采样：`battle.log` 发摘要而非逐条
- 例如按 `(fromId, skill)` 在 200ms 窗口内聚合伤害，或只发暴击/击杀/BOSS 事件。
- 好处：payload 直接降一个量级。
- 代价：信息损失；需要定义「战斗日志面板」到底要什么（当前 `BattlePanel` 的日志渲染是逐条 `LogEntry`）。

### E. 服务端订阅开关 / 频道过滤
- 客户端用 Action 订阅（如 `battle.subscribe { channels, minValue }`），服务端只推订阅内容。
- 好处：按需推送，最省带宽。
- 代价：新增请求 Action（`battle` 段）、订阅状态归属（会话级）、断线重连重订阅；复杂度最高。

### 附加（无论选哪个都建议）：把 batcher 指标接进 `/api/metrics`
- `metrics.service.ts` 增加 `push_flushed_total / push_dropped_total / push_resync_total / push_pending_frames` 等（现成的 `batcher.stats`）。
- 满足 I5，且能验证新通道有没有溢出。

## 5. 硬约束与门禁（违反即不合格）

1. **提交信息禁止 `Co-Authored-By`**。
2. `pnpm run build` + `pnpm run typecheck` + 全量 `pnpm run verify` = 0；**用例只增不减**。
3. **冻结契约只许加可选字段**（`packages/protocol/src/**`）。删/改 `WorldTickDto.events`、
   `BattleEventDto` 形状、`BATTLE_CMD` 常量都要显式批准并同步前端与测试。
4. **逻辑服边界**（AGENTS §16）：事件产生在 battle 服；推送只经 shared 的 `NOTIFICATION_BATCHER`；
   跨服不得深路径 import；`logic-server-boundary.test.ts` 必须绿。
5. **无裸 `Math.random()` / `Date.now()`**（game-core）。
6. **前端零推导**：只渲染服务端下发的事件字段。
7. **容量不变式**（AGENTS §16.3）：I2 任何「每轮处理 N 个」循环必须给出全局预算 + 超载行为；
   I3 禁止静默降级（丢帧/截断要有日志 + 指标 + 动作）；I5 每个限额在 `/api/metrics` 可见。
8. 数据层无改动则 `_shapes.gate.ts` 自然不受影响；若动了 `data/**` 视图必须仍绿。
9. DB 冒烟 6 项（route-probe 28/28 / metrics 9/9 / ws-protocol 15/15 / game-flow 22/22 /
   character-scope 10/10 / map-controller 15/15）。`loot-rule-smoke.mjs` 也可用（需 `LOOT_WINDOW_MS` 放宽）。
10. 改前端后必须 `curl` 5273 的模块并 grep **新版本独有运行期符号**（AGENTS §7.5）。

## 7. 待拍板的决策清单

1. 日志走**独立通道**还是**继续搭 tick**？若独立，`WorldTickDto.events` 是**保留但停用**还是**删除**（契约）？
2. 独立通道是**全量**还是**按事件类型分流**（C）？若是 C，分流规则是什么？
3. 事件**粒度**：逐条 vs 窗口聚合/采样（D）？
4. **频率**：与 tick 同为 5Hz，还是独立节流（更细/更疏）？
5. **上限/丢帧**：单帧最多多少条事件？超出是截断（要有指标）还是丢弃整帧？
6. **断线补偿**：重连后是否需要补拉（新增拉取 Action），还是只保证后续帧？
7. **过滤/订阅**（E）：需要吗？需要的话订阅粒度与状态归属？
8. **离线报告**是否复用同一份事件集合（当前 `OfflineReportDto` 与在线事件同源 `BattleCollector`）？
9. **观测**：batcher 指标接 `/api/metrics` 的字段名与口径；日志丢帧是否单独计数？
