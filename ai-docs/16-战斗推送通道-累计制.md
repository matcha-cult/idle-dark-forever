## 1. 问题

`(world, tick)`（cmd 30 / subCmd 5）此前**每 200ms 无条件推整份 `units` 快照**，战斗日志搭在同一帧的
`events` 字段里。两个后果：

1. **体积**：实测 `units` 占帧字节 **88%~91%**，其中**每单位 64%（170B/264B）是出生后永不变的标识字段**
   （`id/kind/typeKey/name/camp/level/quality/maxHp/…`），每秒被重发 5 次。
2. **无意义推送**：窗口内没有任何变化时照样推一整帧（实测 **62%~67% 的窗口其实是完全静默的**）。

同时 `battle.log`(40/1) 是「已声明但服务端从不发送」的死通道，`battle.loot`(40/2) 是唯一真正在推的战斗推送。

## 2. 设计（已拍板）

### 2.1 模型

> **状态是采样（净差分，5Hz 采样率），日志是全保真（逐条、有序、同帧送达）。**

四条用户约束 → 直接推出四个设计决定：

| 约束 | 推论 |
|---|---|
| 战斗按**累计制** | 200ms 是累计窗口；窗口内所有产出并入同一窗口结算，状态用**净差分** |
| 状态**有变化才推** | 窗口末净变化为空 ⇒ **整帧不入队**（不是发空帧） |
| **无变化不推送** | 不发明心跳帧；保活走 WS ping + `system.ping`(15s) |
| **每 200ms 最多 1 次** | ⇒ 必须**物理单帧**：玩家状态 / 怪物状态 / 日志 / 掉落是**同一帧里的分区**，不是多条路由 |

最后一条尤其关键：若拆成 4 条物理路由，战斗中会有 2~3 条同时非空 ⇒ **10~15 msg/s**，
比改造前的 5 msg/s **更差**（差分后载荷只剩几十字节，77B 信封反而成了主要成本）。

### 2.2 帧格式

`WorldTickDto`（全部为**新增可选字段**，冻结契约只加不改）：

```ts
{
  serverTime: number;
  units: UnitStateDto[];   // @deprecated P2 起停填，恒为 []
  events: BattleEventDto[];// @deprecated P2 起停填，恒为 []
  gainedExp, gainedGold, wave?, bossEvery?;
  seq?: number;            // 会话内单调帧号（观测/调试）
  patch?: UnitPatchOpDto[];// 有序单位补丁
  log?: BattleEventDto[];  // 本窗口战斗日志
  loot?: LootDto[];        // 本窗口掉落（原 40/2 并帧）
}

type UnitPatchOpDto =
  | { op: 'reset'; units: UnitStateDto[] }   // 基线：清空重填
  | { op: 'add';   unit: UnitStateDto }      // 新出现（含全部静态字段）
  | { op: 'chg';   id: string; fields: Partial<UnitStateDto> }  // 仅变化字段
  | { op: 'del';   id: string };             // 从 units 移除（= 清尸，不是死亡）
```

`patch` 是**有序操作流**：同批多帧合并 = **数组直接拼接**，客户端按序应用即语义正确
（含 `add A` 后 `del A` 这类抵消）。这比「按 id 归并」简单且不会错。

### 2.3 可变字段白名单（唯一真相）

`packages/server/src/modules/logic/world/internal/unit-state-diff.ts#MUTABLE_UNIT_FIELDS`（9 个）：

```
hp  mp  rp  ep  comboPoint  targetId  castingProgress  buffs  camp
```

- 其余 11 个字段出生即固定，只在 `add`/`reset` 里出现 —— 这就是 64% 的省法。
- ⚠️ **`camp` 必须在列**：死亡 `enemy → ghost`；中立怪被攻击参战 `neutral → enemy`。
- ⚠️ `buffs` **归一化后比较**（按 `key` 排序），否则顺序抖动会让静默率归零。

### 2.4 死亡 ≠ 移除

引擎实证：`Unit.kill()` 只把 `camp` 翻成 `ghost` 并清资源/目标/Buff/读条；
`EnemyUnit.clean()` 才 `world.removeUnit`（默认**死亡后 3000ms**，且 `willClean` 钩子为假时**可能永不触发**）。

- 死亡 → 一帧 `chg { alive:false, hp:0, camp:'ghost', … }`；清尸 → 一帧 `del`。
- 新增可选 `UnitStateDto.alive`，由服务端按 `camp === Camps.ghost` 派生；`hp` 夹到 `>= 0`。
- 前端判死唯一入口 `world-store.ts#isDead()`；**不得**假设「每个 add 最终必有 del」。

### 2.5 静默抑制与丢帧自愈

- 判据唯一实现：`unit-state-diff.ts#worldFrameOf()`（返回 `null` = 不发）。
- **累计器只在入队成功后才清**（`collector.snapshot()` 取、`drain()` 清）。
  静默窗口若误清会**永久丢失日志与经验** —— 这是本设计最危险的一条，已有单测钉死。
- **入队失败（batcher 丢弃）⇒ 不前进基线、不清累计器**，下一窗口重发，客户端自动追平。
  比「依赖 batcher `onResync` 补推」更简单且不依赖跨模块接线。
- 客户端不需要 `seq` 断链检测；若收到指向未知 id 的 `chg`（基线错位），
  `world-store#applyPatch` 主动重拉一次快照自愈（I3）。

## 3. 实测

### 3.1 切流前基线（全量快照，本机真实服务端）

| | `world.1`（Lv1） | `world.9`（Lv90） |
|---|---|---|
| 帧率 | 4.96/s | 4.92/s |
| `data`/帧 | 1140B | 1297B |
| 其中 `units` | 88.8% | 90.2% |
| 其中 `events` | 2.4% | 2.1% |
| 线上/帧（+77B 信封） | 1211B | 1374B |
| 单连接带宽 | 5.89 KB/s | 6.66 KB/s |
| 单单位 DTO | 264B（静态 170 / 可变 95） | 269B（静态 174 / 可变 96） |

> 结论：**日志只占 2%，拆它没用**；收益全在 `units`，且其中大部分是永不变的标识字段。

### 3.2 P1 影子回放（切流前预测，用真实帧重放）

| | `world.1` | `world.9` |
|---|---|---|
| 完全静默窗口 | 66.1% | 70.2% |
| 发帧时差分 data | 207B（峰值 548B） | 247B（峰值 572B） |
| 窗口均摊线上字节 | 1206B → 96B | 1363B → 97B |

### 3.3 P2 切流后实测（`tmp/measure-p2.mjs`，25s/图）

| | `world.1` | `world.9` |
|---|---|---|
| 帧率 | 1.84/s | 1.64/s |

⚠️ 该峰值**不是最坏值**：未跑到 20 波守关 BOSS（召唤物可破 4 只同屏上限）。

## 6. 已拍板的收尾项

| # | 项 | 结论 |
|---|---|---|
| 1 | 连续量 `remainMs` / `castingProgress` 改绝对时间戳 | **不做**。实测 4 组场景（`world.1` Lv1 / `world.9` Lv90 / `world.13` Lv100 / `world.9` Lv100-120s）中，连续量造成的额外帧占比 **0%**、占用 data 字节 **0~0.2%**、**没有任何单位带过 Buff**。保留 `remainMs` 反而更贴合「前端零推导」，不必开规则豁免。⚠️ 前提：样本是**导入的无装备角色**，构造不出带 Buff 的战斗；若真实装备档观察到 Buff 常驻，再改。详见 AGENTS §20.11。 |
| 2 | `units` / `events` 停填但保留 | **保留**（不破坏冻结契约）。代价 20B/帧 ≈ 0.035 KB/s；删除需显式批准。 |
| 3 | 单图单位数无上界（违反 I2） | **已修**：新增 `MAX_UNITS_PER_WORLD = 32` 硬顶 + 明确的超载行为（拒绝注册 + 计指标 + 发事件），刷怪器与 BOSS 刷新都在调用前拦。详见 AGENTS §20.10。 |
| 4 | `(battle, log)`(40/1) 与 `(battle, loot)`(40/2) 闲置 | **保留**，登记为将来的「订阅通道」（届时订阅表现为「服务端在单帧内裁剪分区」，不增加消息数）。 |
| 5 | 20 波 BOSS 波的最坏帧未实测 | **风险已由 #3 兜住**：单帧上界 = `MAX_UNITS_PER_WORLD × 单单位 DTO` ≈ 32 × 264B ≈ **8.4KB**（仅 `reset` 帧的悲观上界）。仍建议后续实测一次以核对。 |

## 7. 后续修正（实机反馈）

P2 切流后的实机试玩暴露了三个**日志显示**问题，均已修复（硬约定回写 `AGENTS.md` §21）：

| 现象 | 根因 | 修法 |
|---|---|---|
| 日志是倒叙的，但滚动条只钉在最下 | `LogPanel` 按「旧在上、追尾阅读」写（`slice(len-maxItems)` + `scrollTop = scrollHeight`），与 `world-store` 的「新在最前」契约**相反** | `LogPanel` 改为**截断丢尾部** + **`scrollTop = 0`**，与 store 契约对齐 |
| 敌方单位只显示原始 id（`3 → 艾尔 melee 0`） | 渲染时用**当前单位表**建 `id → name`；但日志是历史、单位表是当下（尸体 3s 后被清）。实测 **41%** 的引用查不到名字 | `world-store` 增加 `unitNames` **历史注册表**（上限 512，插入序淘汰）+ `world.nameOf()`；实测 **41.0% → 0.0%** |
| `enemy.appear:大史莱姆` / `map.enter:…` 等内部标记直出 | `general` 事件的 `key:参数` 文案未做展示映射 | 新增 `formatGeneralText()`：已知前缀中文化，**未知前缀原样透出** |

顺带修掉第四个：战斗数值沿用了 `formatAmount` 的**整数截断**，而怪物一击常 < 1 →
日志满屏 `melee 0`。新增 `formatBattleValue()`（`|值| < 100` 的小数保留 1 位）。

验证：`pnpm run verify` = 0，**1435 用例**（web 106 / ui-kit 195）；前端 dev server curl
三种模块均命中**新版本独有运行期符号**（`slice(0, maxItems)`、`scrollTop = 0`、
`formatGeneralText`、`formatBattleValue`、`unitNames`）。

## 8. 后续修正（第二批实机反馈：技能名与伤害取整）

| 现象 | 结论与做法 |
|---|---|
| 日志显示 `thumpHead` / `meleeForRage` 这类**技能表键** | 技能表 **132 条**，前端镜像必然漂移。改为**内核解析**：`battle-world#skillNameOf()` 从 `tables.skills[skill.type].name` 取名，随事件下发 `skillName`（`damage`/`heal`/`dodge` 三个变体各加可选字段）。实测：`melee`→攻击、`thumpHead`→重击·击颅、`meleeForRage`→怒击。缺失时前端回落键本身（缺失可见）。 |
| 日志出现 `26.7` / `1.1` / `0.4` 这类**小数伤害** | 先查证：**原版也不取整**（`world.js#sendDamage` 的 `(value - absorbed) / (1 + def/200)` 全程浮点），移植是忠实的 —— 所以这是**主动的设计变更**，不是修 bug。产品要求「不允许小数位伤害」。 |

**取整口径**（唯一入口 `roundCombatValue()`，在 `sendDamage` / `sendHeal` 处生效）：

- 非有限（`NaN` / `±Infinity`）→ **0**。原版不校验，`NaN` 会经 `hp -= v` 把血量污染成 `NaN`、
  整场战斗报废；既然已经在结算处取整，就把这条边界顺手收紧（`boundaries.test.ts` 已改写）。
- `> 0` → `max(1, round(v))`。**正的至少 1**：只做 `round` 会得到 `0.4 → 0`，
  于是日志出现 `melee 0`（此前正是被投诉的现象），更糟的是**打不死的怪会让挂机卡波次**。
  代价：`< 1` 的伤害被抬高（实测怪物打高防玩家常在 0.4~1.5 → 变成 1~2），
  **坦度收益被削弱**；若要改口径，改这一个函数即可。
- `< 0` → 对称取整 `-max(1, round(|v|))`：保留原版「负伤害 = 治疗」语义，只把它整数化。
- `0` → 0（被护盾完全吸收的真实 0 伤害，不能被抬成 1）。

⚠️ **事件值与实际扣除的 HP 必须是同一个整数**（否则日志与血条长期对不上）。
⚠️ **只作用于经 `sendDamage` / `sendHeal` 的伤害与治疗**；数据层里直接改 HP 的百分比 / 回复
效果（`hp -= maxHp * 0.3`、`hpRecovery * RECOVERY_RATE`）不是「伤害数值」，保持原样 ——
因此 HP 仍可能带小数尾巴，这不影响日志。

**代价**：三个金样常数重录（`0x6f3847b3/0xf7d493b3/27` → `0x255e00d0/0x248e509e/20`）。
取整改变了事件数值，战斗时序随之**分叉**（拿掉取整做对照：玩家会在 30s 内阵亡并产生
`death`/`exp`；开启取整则存活、无击杀）—— 这正是金样回归的价值所在。

**实机验证**：`world.1` 25s 抽样，伤害值集合 = `{1, 5, 6, 8}`（无小数），
且事件同时带 `skill: "melee"` + `skillName: "攻击"`。
