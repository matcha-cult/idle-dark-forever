> **用途**：在动手改推送协议之前，把「现在到底发了什么」逐条钉死 —— 消息种类、字段、每种情况的真实报文、频次与字节。

>
> **生成方式**：全文报文来自**真实服务端抓包**（后端 3100，一次性新账号，未触碰任何现有角色），
> 不是手写示例。抓包脚本 **`packages/server/scripts/capture-tick.mjs`**（已入库，可重跑），
> 原始数据 `packages/server/tmp/capture-mubg2y3kwywe.json`（90s，179 帧，gitignore 的本地产物）。
> 凡**没有抓到、只能从代码路径推断**的，第 5 节单独列出并明确标注，不与实测混在一起。
>
> **抓包环境**：`world.1`（边境荒野，地图等级 1）、战士 Lv.1 → Lv.3、EXPRATE=100（dev 配置，
> 所以升级很快，便于观察升级帧）、装备全空（无 Buff / 无法术技能，因此 `heal` / `buff` 事件没出现）。

## 0. 结论速查

1. **战斗状态下只有一条推送**：`(world, tick)` = `cmd 30 / subCmd 5`，信封 `kind:'notification'`。
   实测 90 秒内「其它推送」= **0 条**。
   - `(battle, log)` 40/1 与 `(battle, loot)` 40/2 **服务端从未发送**（P2 起并帧进 tick）；
   - `(career, levelup)` 80/7 有实现但**没有任何调用方**（死代码）；
   - `(inventory, changed)` 50/9 只在**面板写操作**（装备/出售/生产）时发，战斗过程中不发。
2. **敌方单位有两种下发形态**：
   - **全量**：`world.snapshot`(30/1) 与 `world.enterMap`(30/2) 的**请求响应**里带 `units[]`（此刻的全部单位）；
   - **增量**：`(world, tick)` 的 `patch` 分区，四种操作 `reset / add / chg / del`。
   **新怪出现永远是一条 `add`，且 `add` 携带该单位的全部字段**（不是只带变化字段）。
3. **单位字段分两档**：出生即固定的只在 `add/reset` 出现一次；17 个可变字段才会出现在 `chg`（见 §2.3）。
   ⚠️ `alive` **不在**可变白名单里 —— 它只在 `add/reset` 出现且恒为 `true`，死亡靠 `camp:'ghost'` 表达。
4. **一帧里可以同时有多个分区**：`patch` + `log` + `loot` + `gainedExp/gainedGold` + `wave` + `bossPending`。
   也可以**只有日志没有状态变化**（如闪避帧 `patch:[]`），或**只有状态没有日志**（如仅怒气回复）。
5. **实测频次与体积**：90s 内 179 帧 = **1.99 帧/s**（5Hz 窗口的 39.8%，即**静默窗口 60.2%**）；
   线上消息体（含信封）最小 **278B**、平均 **400B**、最大 **1254B**。
6. `units` / `events` 两个字段**每帧仍在发**，恒为 `[]`（约 20B/帧的历史包袱）。

| 140/1~5 `chaos.*` | **无推送** | 全是请求/响应（`state` / `setSequence` / `setFailMode` / `start` / `stop`），与野外战斗无关 |

> 实测佐证：90s 抓包里 `otherNotifications` 为空数组，即**期间只有 30/5**。

### 1.3 `(world, tick)` 的三个发送时机（不是所有 tick 都会发）

服务端每 **200ms** 跑一轮（`WORLD_CONFIG.tickIntervalMs = 200`），每轮对每个在线会话组一帧。
`worldFrameOf()` 决定这一帧**发不发**：

```
有内容 = patch 非空 ∨ log 非空 ∨ loot 非空 ∨ gainedExp ≠ 0 ∨ gainedGold ≠ 0
        ∨ wave ≠ 上次已发的 wave ∨ bossPending ≠ 上次已发的 bossPending
无内容 ⇒ 返回值 null ⇒ 这一轮【一条消息都不产生】
```

所以「很久没有帧」是**正常状态**，不是断线。

## 2. 敌方单位是怎么下发的

### 2.1 全量形态（请求响应，不是推送）

进图 / 拉快照时，`units[]` 给出**当前全部单位**（玩家 + 场上怪物）。

`world.snapshot` 在 `home`（未进图、无怪）的响应：

```json
{"success": true, "data": {"map": "home", "units": [{"id": "1", "kind": "player", "typeKey": "7c625dbc-7047-4317-a1f9-3a1dd73982c3", "name": "艾尔", "camp": "player", "level": 1, "quality": 0, "hp": 60, "maxHp": 60, "mp": 0, "maxMp": 0, "rp": 0, "maxRp": 0, "ep": 0, "maxEp": 0, "comboPoint": 0, "targetId": null, "castingProgress": null, "buffs": [], "alive": true, "attributes": {"careerName": "战士", "maxLevel": 100, "str": 11, "dex": 9, "int": 4, "atk": 6.5, "atkSpeed": 0.4, "speedBonusPct": 0, "critRatePct": 5, "critBonusPct": 150, "dmgBonusPct": 0, "hpFromKill": 0, "mpFromKill": 0, "expBonusPct": 0, "skillExpBonusPct": 0, "magicFindPct": 0, "goldFindPct": 0, "dodgeRatePct": 2.9, "def": 11, "fireResist": 4, "coldResist": 4, "lightningResist": 4, "chaosResist": 0, "fireAbsorbPct": 0, "coldAbsorbPct": 0, "lightningAbsorbPct": 0, "chaosAbsorbPct": 0, "meleeAbsorbPct": 0, "hpRecovery5s": 10, "mpRecovery5s": 0, "rpRecovery5s": -5, "epRecovery5s": 0, "rpRecHp": 0, "leech": 0}, "exp": 0, "maxExp": 10.3}], "maps": [ ... ], "updateRate": 1, "paused": false, "wave": 0, "bossEvery": 20, "bossPending": false}}
```

`world.enterMap {map:'world.1'}` 的响应结构完全相同（`map` 变成 `world.1`；进图那一刻**还没有怪**，
下一波由刷怪器的定时器产出，所以 `units` 里只有玩家）。

### 2.2 增量形态：`(world, tick).patch`

`patch` 是**有序操作流**，客户端必须按序应用：

| op | 载荷 | 语义 |
|---|---|---|
| `reset` | `{op:'reset', units: UnitStateDto[]}` | 清空本地单位表并重填（**会话首帧 / 基线重建**） |
| `add` | `{op:'add', unit: UnitStateDto}` | **新单位出生**（携带全部字段，含出生即固定的标识字段） |
| `chg` | `{op:'chg', id, fields: Partial<UnitStateDto>}` | 只带**变化字段**（白名单见 §2.3） |
| `del` | `{op:'del', id}` | 从单位表**移除** = 清尸（**不是死亡**，死亡是 `chg{camp:'ghost'}`） |

**新怪出现的完整链路**（`game-core/combat/spawner.ts`）：
`Born.onTimer` 到点 → 先查 `atMonsterCap() || world.atUnitCap()`（硬顶 32）→ `world.addEnemy(...)` →
下一帧差分发现新 id ⇒ 一条 `add` + 一条 `general` 日志 `enemy.appear:<名>`。

### 2.3 单位 DTO 字段表：哪些字段会变

`UnitStateDto`（`packages/protocol/src/dto.ts`）。「出现位置」列的含义：
- **add/reset** = 只在下发整份单位时出现（出生即固定，或只在重建基线时出现）；
- **chg** = 每帧差分时**可能**单独下发。

| 字段 | 类型 | 出现位置 | 说明 |
|---|---|---|---|
| `id` | string | add/reset | 服务端分配的稳定 id（**世界内自增**，每个世界实例从 1 开始；两次抓包里玩家都是 `"1"`） |
| `kind` | string | add/reset | `'player' \| 'enemy' \| 'summon'`（`unitKindOf()` 按身份判，**不是阵营**） |
| `typeKey` | string | add/reset | 敌方 = 敌人 key（如 `slime.minimal`）；玩家 = 角色 UUID |
| `name` | string | add/reset | 显示名（含 `displayName` hook 的结果） |
| `camp` | string | **chg** | 七种：`player` / `alien`（联军）/ `enemy` / `neutral`（可打不自动）/ `ghost`（尸体）/ `story` / `shrine`。**死亡与中立参战都靠它** |
| `level` | number | **chg** | 玩家升级会变 |
| `quality` | number | add/reset | ⚠️ **敌人词缀条数**（可 >2），与装备品质同名不同义 |
| `hp` / `maxHp` | number | hp=**chg**，maxHp=**chg** | `hp` 投影时夹到 `>= 0`；`maxHp` 玩家升级会变 |
| `mp` / `maxMp` | number | **chg** | — |
| `rp` / `maxRp` | number | **chg** | 怒气（战士的 `rp` 每帧都在变，是最常见的帧） |
| `ep` / `maxEp` | number | **chg** | 能量 |
| `comboPoint` | number | **chg** | 骑士圣能 |
| `targetId` | string \| null | **chg** | 当前目标 |
| `castingProgress` | number \| null | **chg** | 0..1；无读条为 `null` |
| `buffs` | array | **chg** | `{key,name,stack,remainMs}`；比较时按 key 归一化 |
| `boss` | boolean? | add/reset | 守关 BOSS 标记；非 BOSS **省略该键** |
| `alive` | boolean? | add/reset | ⚠️ 投影按 `camp === 'ghost'` 派生；**不进可变白名单**，故 `add` 里恒为 `true`，死亡由 `camp:'ghost'` 表达（前端 `isDead()` 有回落） |
| `attributes` | object? | **chg** | **仅玩家单位**，34 项展示投影（见上一批交付） |
| `exp` / `maxExp` | number? | **chg** | **仅玩家单位** |

**可变白名单（17 个，唯一真相 `server/.../unit-state-diff.ts#MUTABLE_UNIT_FIELDS`）**：

```
hp mp rp ep comboPoint targetId castingProgress buffs camp
level maxHp maxMp maxRp maxEp exp maxExp attributes
```

> 只有这 17 个字段会出现在 `chg.fields` 里。**其余字段改了也不会下发** ——
> 这就是为什么 `alive`、`name`、`quality`、`boss`、`kind`、`typeKey`、`id` 改不动（要改就得重建基线 `reset`）。
> 实测 90s 抓到的 `chg` 字段集合共 9 种（见 §4.18）。

## 3. `(world, tick)` 报文结构

### 3.1 信封

```json
{"kind": "notification", "cmd": 30, "subCmd": 5, "data": { ... }, "timestamp": 1790006960790}
```

- **没有 `type` 字段**（前端按 `(cmd, subCmd)` 路由）；
- `timestamp` 是推送产生时刻；`data.serverTime` 是**世界逻辑时间**（客户端对时用它）。

### 3.2 `data` 字段表（序列化顺序即此顺序）

| 字段 | 类型 | 是否总是存在 | 说明 |
|---|---|---|---|
| `serverTime` | number | 是 | 服务端毫秒时间戳 |
| `units` | UnitStateDto[] | 是 | ⚠️ **@deprecated，恒为 `[]`**（P2 前是整份快照） |
| `events` | BattleEventDto[] | 是 | ⚠️ **@deprecated，恒为 `[]`** |
| `gainedExp` | number | 是 | 本帧累计经验增量（供 HUD 角标，**不是权威值**） |
| `gainedGold` | number | 是 | 同上 |
| `wave` | number | 是 | 当前**已完成**波数 |
| `bossEvery` | number | 是 | 守关 BOSS 间隔波数，恒 `20` |
| `bossPending` | boolean | 是 | 本图 BOSS **是否还会出现**（通关后 `false`，UI 不再显示倒计时） |
| `seq` | number | 是 | 本会话帧序号，从 1 单调递增（仅观测/调试） |
| `patch` | UnitPatchOpDto[] | 是 | 本窗口单位净差分（可空数组） |
| `log` | BattleEventDto[] | 是 | 本窗口战斗日志（按发生顺序） |
| `loot` | LootDto[] | 是 | 本窗口掉落 |

### 3.3 `log` 的七种事件（`BattleEventDto`）

| kind | 字段 | 说明 |
|---|---|---|
| `damage` | `fromId, toId, damageType, skill, skillName?, value, crit, absorbed` | `value`/`absorbed` 是**浮点**（展示层 `Math.round`） |
| `heal` | `fromId, toId, skill, skillName?, value` | — |
| `dodge` | `fromId, toId, skill, skillName?` | 闪避，无伤害 |
| `death` | `unitId, name, camp` | 单位死亡 |
| `buff` | `unitId, buffKey, name, on` | Buff 获得 / 消失 |
| `exp` | `amount, level, whoId?` | 获得经验 |
| `general` | `text` | **字符串协议**：`key:参数…`，前端解析。已知前缀：`map.enter:<key>:<名>`、`enemy.appear:<名>`、`player.death:<名>:<秒>`、`world.unitCap:<type>` |

### 3.4 `loot` 条目

```json
{"slot": { ...整份 InventorySlotDto... }, "handled": "pickup|sell|decompose|lost", "gold?": 0, "materials?": [...]}
```

## 4. 逐个情况列举（均为真实抓包）

> 下面每条都是 90s 抓包里的**原始 `data`**（已按需截断超长数组，未改动字段与数值）。
> 「出现次数」是 90s 内的帧数。

### 4.1 静默窗口：**一条消息都不发**

判据见 §1.3。玩家的目标已选定、怒气满、怪物没受到伤害时，连续多个 200ms 窗口无净变化。
实测：450 个窗口里 271 个静默（**60.2%**）；`/api/metrics` 的 `world_push_quiet_skips_total` 会累加。

### 4.2 会话首帧：`reset`（唯一一次，1166B）

**触发**：`player.select` 启动世界会话后，**在客户端拉快照之前**第一个 200ms 窗口就到了（`needsReset=true`）。
若客户端先发 `world.snapshot`/`world.enterMap`，服务端会把该快照当作基线并撤销 reset ⇒ 就看不到这一帧。
（这正是「先 select 再拉快照」的竞态，抓包时用 sleep 复现。）

## 7. 如何复现这套报文

```bash
# 后端需在跑（dev 配置端口 3100）
cd packages/server
node scripts/capture-tick.mjs <秒数> 3100 <首帧前等待ms>
# 例：node scripts/capture-tick.mjs 90 3100 1500
```

- 脚本会**注册一个一次性新账号**（`capture_<时间戳>`）并建角，**不触碰任何现有角色**；
- `<首帧前等待ms>` 用来复现 §4.2 的 `reset` 竞态：`player.select` 之后先等一会儿再拉快照；
- 输出 `packages/server/tmp/capture-<stamp>.json`：包含
  `homeSnapshot` / `enterMapWorld1` / 每种帧形状的首个**原始信封** /
  `chg` 字段集合分布 / 日志 kind 分布 / 字节分布 / 抓包前后的 `/api/metrics`。

## 9. 审阅时值得注意的点（候选修改项，等你拍板）

1. **`units` / `events` 两个 deprecated 空数组仍占每帧 ~20B**（278B 的最小帧里约 7%）。
   要删就得动冻结契约（加字段可以，删字段不行）。
2. **`alive` 不在可变白名单**：`add` 里恒 `true`，死亡只体现为 `camp:'ghost'`。
   前端现在靠回落判定，能用；但如果希望「死亡」有一个显式布尔信号，需要把 `alive` 加进白名单
   （代价：每帧多比一个字段，死亡帧多带 `alive:false`）。
3. **`enemy.appear` / `map.enter` 走 `general` 字符串协议**（前端解析 `key:参数`）。
   要新增字段（如敌人等级/词缀）就得改成结构化事件 —— 目前 `general.text` 里只有名字。
4. **`damage.value` / `hp` / `exp` 都是浮点**，取整在展示层。如果希望线上就是整数，得改投影（会动平衡口径）。
5. **`attributes` 整份重发（540B）**：只在真变化时发，但一次升级帧因此到 1.25KB。
   可选：改成按字段增量（协议要新增 `chg.attributes` 的局部更新语义）。
6. **`loot.slot` 是整份 `InventorySlotDto`**（含 `description`/`affixes`），单条约 300B。
   掉落多了会明显放大帧；可选：只发 `key/count/name/handled`。
7. **`rp`（怒气）驱动了大量「噪声帧」**：**只**改 `rp` 的帧 128 条，占全部 179 帧的 **71%**。
   如果频次是关注点，可以考虑对连续量做阈值/降频（但要小心 HUD 观感）。
8. **`wave` 是「已完成波数」**（打完才 +1），与 UI 文案「波次 N」的对应关系需要确认是否一致。
9. **`(career, levelup)` 是死代码**（有实现无调用方）；升级目前只能靠 `patch.level` 感知。
   要么接上，要么删掉。
10. **`battle.focus` 没有任何回执**（`ActionResult<null>`），玩家点怪后要靠下一帧 `targetId` 才知道生效。

## 附：W11 增补（本文写于 W11 之前，以下为差异）

> 本文 §1–§8 的报文实例与频次统计基于 W11 **之前**的代码，仍然有效；下面是 W11 引入的增量。

1. **单位 DTO 新增两个出生字段**：`UnitStateDto.elite?: boolean` 与 `UnitStateDto.rarity?: number`
   （0 普通 / 1 稀有 / 2 精英 / 3 传奇，**服务端派生**）。二者与 `boss?` 同组 ——
   **只在 `add` / `reset` 出现一次**，**不进** `MUTABLE_UNIT_FIELDS`，因此**不增加稳态流量**
   （只在单位出生那一帧多约 20~30B）。§2.3 的字段表与 §4.4 的 `add` 样例需按此补充。

   因此 §4 里「第 20 波 BOSS 现身」的样例之外，会新增一种 **精英现身**（`add` 且 `rarity: 2`）形状。

   静默窗口比例预计不变（精英/里程碑只在特定波次产生变化）。
