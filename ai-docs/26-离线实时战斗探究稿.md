## 0. 结论（TL;DR）

1. **用户要的是 `00 §8.3` 的 C3「后台持续推进」，不是 C1/C2。** 现状实现的是 C1/C2
   （玩家回来时一次性有界快进 + 速率外推），而且因为锚点被提前重置，连 C1/C2 也拿不到时长
   （见 §1）。这与用户的初衷（组队时离线一方不应等上线再结算）**方向相反**。
2. **技术障碍很小、成本已被实测证明可承受**：把 `WorldService.tickSession` 首行的
   「离线即早退」改成「离线照常 `stepPaused`，只是不推送」即可让世界持续跑。
   实测（本机，`game-core` dist，与 `tickSession` 完全相同的驱动方式）：
   **单角色单 tick ≈ 2.6–3.5 µs**；2000 个常驻角色一轮（200ms）约 **5–7 ms**，
   仅占 `maxRoundCpuMs=40ms` 的 **13%–17%**。
   同时已用最小复现验证：**只推时钟就能真的击杀/升级/掉落**（1 级角色 10 虚拟分钟
   击杀 44 只、升到 3 级）—— 见 §7 / §7.1。
3. **真正的难点是四件事**，不是 tick 成本：
   - **推送隔离**：离线会话不能再按 `userId` 入 batcher，否则会推给同账号当前在线的
     另一个角色（§15 串号回归）。必须引入「角色级附着」判定。
   - **锚点纪律**：`Player.timestamp` 必须精确等于「已被模拟/结算到的虚拟时刻」，否则
     实时模拟与 idle 兜底会**双重计收益**。
   - **生命周期与容量上限**：常驻会话会无界增长；要有「热/冷/结算兜底」三态 + LRU + 指标
     （I2/I3/I5）。
   - **重连语义**：`resetActiveCharacter`（每次 WS 握手）现在会 `stop()` 会话，必须改成
     「脱离连接但不销毁」，否则一刷新就把连续模拟打断。
4. **推荐架构**：把「**模拟**」与「**连接**」解耦为两个概念 ——
   `WorldRuntime`（常驻，按策略 hot/cold）+ `Attachment`（谁在收推送）。
   这是组队战斗的前置重构；之后的 `Encounter`（一个 `BattleWorld` 挂 N 个 `PlayerUnit`）
   可以在此之上落地，而**不需要再改 tick 循环**。分三期见 §9。

## 2. 方案空间

| 方案 | 做法 | 保真度 | CPU/内存 | 组队可组合性 | 结论 |
|---|---|---|---|---|---|
| **A. 常驻实时模拟（推荐）** | 会话常驻，离线也按 5Hz `stepPaused` 真实推进；只关推送 | 与原版一致 | 已实测可承受（§7） | ✅ 天然可组合（离线队员一直在世界里） | **采用** |
| B. 周期批量追帧 | 每 N 秒对离线角色一次性补 N 秒虚拟时间 | 中（步长大、事件聚簇） | 更低 | ❌ 队友的交互事件无法与离线方对齐 | 仅作 A 的降频档 |
| C. 独立离线 worker/进程 | 把离线模拟挪出主事件循环 | 同 A | 隔离性最好 | ⚠️ 需跨进程共享世界（未来多实例才需要） | 阶段 3 可选 |
| D. 只修锚点、保留 C1/C2 | 回到"回来一次性结算" | 低 | 最低 | ❌ 与用户目标相反 | 否 |

> B 看似省 CPU，但组队的语义要求「离线队员的状态在**任意时刻**都接近在线队员」；
> 大粒度补帧会让离线方在补帧间隙"不存在"，队友打不到它、它也不吃伤害。
> C 是 A 的进程级放大，不改变模型，只改部署。

## 3. 推荐架构（P0：解耦「模拟」与「连接」）

### 3.1 概念

```
WorldRuntime (= 现有 WorldSession + 政策字段)         Attachment
┌─────────────────────────────────────────┐        ┌──────────────────────────────┐
│ battle World | Clock | Collector         │        │ activeByUser: userId→charId  │
│ lastTickAt / carryMs / advancedMs        │◄──────►│ onlineSessions.isOnline      │
│ anchor(=player.timestamp) 纪律            │        │ 推送只发给 attached 的 runtime│
│ simState: hot | cold                     │        └──────────────────────────────┘
│ awaySummary（脱离期间累计收益）            │
└─────────────────────────────────────────┘
```

- **hot**：每个 tick 轮都 `stepPaused`（在线角色、战斗图中的离线角色、组队被 pin 的角色）。
- **cold**：保留在内存但不再推进（安全区离线、被容量上限挤出的候选；可在需要时重新 hot）。
- **settlement 兜底**：runtime 不存在或 cold 的时段，由现有 `IdleService` C1/C2 补（见 §5.3）。

### 3.2 唯一判定入口（新增纯函数，放 `world/internal/`）

```ts
// isAttached：只有它决定"是否推送"。账号在线 且 该角色是当前角色。
export function isAttached(input: {
  onlineAtAccount: boolean;   // onlineSessions.isOnline(userId)
  activeCharacter: string | undefined;
  characterId: string;
}): boolean {
  return input.onlineAtAccount && input.activeCharacter === input.characterId;
}

// shouldSimulate：决定"是否 hot"。战斗区域 → 常驻；安全区 → 冷却。
export function shouldSimulate(input: {
  isCombatArea: boolean;
  pinnedByParty: boolean;     // P2 起接入；P0 恒 false
  withinCap: boolean;
}): boolean { ... }
```

> ⚠️ **必须用 `isAttached` 而不是 `onlineSessions.isOnline(userId)` 来做推送门**。
> 理由：`sendNotification(userId, …)` 按 userId 扇出到该账号**全部**连接（`AGENTS.md §15`）。
> 若账号在线但当前角色是 B，而 A 的 runtime 仍 enqueue，就会把 A 的战斗帧推给 B 的连接 ——
> 这正是 §15 已修过的串号。把「入队」改成 `if (attached) enqueue else foldIntoAwayAndDrain`。

### 3.3 分轮调度：在线优先，离线吃余量

现有 `tick()` 从 `tickCursor` 绕一圈，全局预算打满即停（`world.service.ts:272-317`）。
离线角色一多，可能**先**把预算吃光、把在线角色挤到下一轮。改法（最小改动）：

```
const onlineKeys  = [...sessions].filter(attached)
const offlineKeys = [...sessions].filter(!attached && hot)
const order = [...rotate(onlineKeys, cursorOnline), ...rotate(offlineKeys, cursorOffline)]
```

- 在线角色**永远先跑**（保证 I1 对在线者成立、5Hz 不掉）；
- 离线角色吃余量，被预算截断时走既有 `carryMs`/债务记账（不丢时间，下一轮补）；
- 组队成员（P2）进入 `onlineKeys` 语义的「高优先」集合；
- 给离线单独一个更小的 `offlineSimBudgetMs`（建议 20ms），超过就**显式**记 metric
  并触发 LRU 冷处理（I3：不静默降级）。

## 4. 关键不变式与风险

| # | 不变式 | 违反后果 | 保障 |
|---|---|---|---|
| **V1 锚点纪律** | `player.timestamp` == 「该角色已被模拟/结算到的虚拟时刻」。hot 时**每 tick** 内存写 `now`，每 30s 落库；`stop/cold` 时写 `now` | 实时模拟与 idle 兜底**双重计收益** | §5.3 + 单测「连续模拟后 pendingOfflineMs ≈ 0」 |
| **V2 推送隔离** | 只有 `isAttached` 的 runtime 才 `batcher.enqueue` | 串号 / 双份战斗帧（§15 回归） | 纯函数 `isAttached` + 单测 |
| **V3 单写者** | 一个角色的 `characters.state` 只有一个写者：其 `WorldRuntime`（hot 时）；cold/无 runtime 时段才由 `IdleService` 写 | 状态回滚 / 丢收益 | hot 与 settle 互斥（§5.3）；`stop` 后 runtime 不存在 |
| **V4 世界时间=真实时间** | hot runtime 的 `ΣadvancedMs/ΣrealMs → 1` | 挂机收益与在线不一致 | 沿用 `planAdvance`；离线纳入同一 `world_time_ratio` 指标（分在线/离线两个桶） |
| **V5 容量有界** | hot 会话数 ≤ 上限；超限有 LRU 冷处理 + 指标 | 内存/CPU 无界增长 | §5.4 |
| **V6 确定性** | 同 seed 同初始档 → 同事件流；实时与 idle 用同一内核 | 反作弊/复算失效 | 复用 `buildBattleWorld`；RNG 状态重启后重置是**已知遗留**（§10 Q4） |
| **V7 边界** | 战斗只在 battle 服；idle 兜底只经 shared 端口 | 架构门禁失败 | `registry.ts` + `TRANSITIONAL_DEEP_IMPORTS` 保持为空 |

## 5. 具体改动清单（P0，文件级）

> 只列**改哪里、改成什么**，不写完整补丁（仓库正被另一会话修改，避免冲突）。

### 5.1 `modules/logic/world/world.service.ts`

1. **删除离线早退**（`:321-322`）：`tickSession` 不再因离线 `return 0`。
2. **新增附着判定**（`:322` 处替换）：计算 `attached = isAttached(...)`。
3. **推进条件**：`attached || shouldSimulate(...)` 才 `stepPaused`；否则只刷新 `lastTickAt`（不欠账）。
4. **推送分流**：把 `emitTick` 拆成 `buildFrame()` + `deliver()`：
   - `attached` → 现有 `batcher.enqueue` 路径（P2 契约不变）；
   - 非 attached → 把 `frame` 的 `gainedExp/gainedGold/log(计数)/loot` 折进
     `session.awaySummary`，然后 **`collector.drain()` + `session.pendingLoot.length = 0`**
     （否则事件数组无界增长）。
5. **锚点每 tick 写**：在 `advanceMs > 0` 分支末尾 `player.timestamp = now`
   （内存；落库仍走 30s `persistIntervalMs` 的 `schedulePersist`，`:386-394`）。
6. **调度优先分区**：`tick()` 先在线后离线（§3.3），游标分两个。
7. **回收策略改写**（`sweepIdleSessions`，`:406-422`）：
   - hot 且战斗图的离线会话：**不回收**（保留连续模拟）；
   - 安全区离线 / 超容量 / 非 hot：按阈值 `stop()`（先 flush 再 dispose，语义不变）。
8. **`resetActiveCharacter` 改为「脱离而不销毁」**（`:796-807`）：
   - 清 `activeByUser` + `panelCharacters`（保持）；
   - `batcher.drop(userId)`（保持）；
   - **不调用 `stop()`**；改为 `schedulePersist(session)`（刷新时落一次库），会话继续 hot。
9. **`stats`**：新增 `offlineSimulated`、`sessionsHot`、`sessionsCold`、`awaySummaryPending` 等（§6）。
10. **`start()` 不再写锚点**（删 `:739` 的 `player.timestamp = now`）：锚点的唯一写者变为
    「hot tick 每 tick 刷新」+「`stop()`/cold」+「`select` 前置缺口结算」。理由见 §5.3 的竞态。

### 5.2 `modules/logic/world/world.config.ts`

新增常量 + 解析（沿用 `parseSessionReapMs` 的严格回落风格）：

```ts
offlineSimBudgetMs: 20,        // 离线模拟每轮 CPU 预算（在线优先用满后再用）
residentHotMax: 8_000,         // hot 会话硬上限（在线+离线；超限 LRU 冷处理）
safeAreaParkAfterMs: 60_000,   // 安全区离线多久后转 cold
sessionReapMs: 15 * 60_000,    // 现有：仅用于非 hot 会话
```

### 5.3 与 idle 域的关系（去重，防 V1/V3 违反）

现状：`idle.report` 以 `now - player.timestamp` 结算（`:145`）。实时模拟后，
**hot 期间锚点被每 tick 刷新**，所以离线返回时 `pendingOfflineMs ≈ 0`，idle 自动不重复发收益。
仍然需要 idle 兜底的三种缺口：

| 缺口 | 覆盖者 |
|---|---|
| 服务端重启 / cold / LRU 挤出期间 | idle C1/C2（锚点=最后一次落库值，误差 ≤30s） |
| 从未创建过 runtime 的角色 | idle C1/C2（首次 `select` 时） |
| 安全区离线 | 零收益（RD1 不变） |

**必须同时修「结算晚于锚点重置」的排序 bug**，而且要处理一个**新竞态**：

> 实时模拟一旦开启，hot 循环**每 tick 都会把锚点推到 `now`**。如果重启后的缺口结算
> 仍然由客户端在 `player.select` **之后**发起（现在的 `loadPanel → idle.report`），
> 那么只要 tick 循环先跑过一次（≤200ms），缺口就被锚点覆盖、`idle.report` 返回 0
> —— 与原始 bug 同类。因此**缺口结算必须发生在世界开始推进之前、且在服务端同步完成**，
> 不能依赖客户端时机。

两种修法：

- **修法 1（推荐，边界最干净）**：在 shared 增加端口 `IDLE_SETTLE_PORT`（token），
  由 idle 服实现、character 服注入；`PlayerLogicService.select` 在 `startSession`
  **之前**：`load` 玩家 → 算 `gap = now - player.timestamp` → `await settle(userId, key, gap)`
  → 再 `start`。`start()` 同时**删除** `player.timestamp = now`（`:739`），
  之后锚点只由「hot tick 每 tick 刷新」+「`stop()`/cold」写。
  - 方向 character → idle → battle 无环（idle 本就注入 `BATTLE_COMMAND`），符合 §16 C3/C5。
  - 语义：缺口恰好结算一次，服务端自己触发，不依赖前端调用。
- **修法 2（最小改动，但有残留竞态）**：`start()` 不再写锚点，由 `select` 先算 pending
  再 `start`，客户端随后 `idle.report` 结算。若 tick 恰好在 `select` 与 `idle.report`
  之间跑过一次，缺口会被吞 —— 只能靠「`start` 后到 `idle.report` 前暂停 hot」
  之类的临时措施，反而更绕。**不推荐。**

### 5.4 容量与冷处理（V5）

- `hot` 数量超过 `residentHotMax` 时，按「离线 > 在线」「detach 时间早者优先」选出
  LRU 候选，转 cold：`player.timestamp = now`（当前模拟进度）→ `stop()`（flush+dispose）。
- 被挤出者的离线时段由 idle 兜底（C1 30min 真模拟 + C2 外推），保真度下降但**正确**。
- 所有挤出/截断都记 metric + `[OVERLOAD]` 日志（I3），绝不静默。
- 在线会话**永不**被挤出（I1）。

### 5.5 `modules/game/.../app.module.ts` / 握手

- `resetActiveCharacter` 的语义从「停会话」变「取消附着」后，注释与 `AGENTS.md §15`
  需同步（刷新不再销毁世界；只清附着与待发帧）。

### 5.6 前端 + 协议（体验层，可选但建议同批做）

- `player.select` 响应增加**可选** `awaySummary`（契约只许加可选字段，§4）：
  离线期间实时模拟的 exp/gold/kills/loots 汇总（服务端权威，前端零推导）。
- `game/stores/idle-store.ts`：`hasPending`（gap 结算）与 `awaySummary`（实时挂机战报）
  分开渲染；`idle.claim` 不再二次发收益（已实时入账），只清汇总。
- `pendingOfflineMs` 语义收窄为「未被实时模拟覆盖的缺口」，保留给重启等场景。

## 6. 可观测性（I5，新增指标）

`metrics.service.ts` 的 `world_*` 组新增：

| 指标 | 含义 | 健康值 |
|---|---|---|
| `world_sessions_hot` / `world_sessions_cold` | 热/冷会话数 | — |
| `world_sessions_online` / `world_sessions_offline_hot` | 附着 / 离线在跑 | — |
| `world_time_ratio_offline`（分桶） | 离线世界时间/真实时间 | ≥0.99 |
| `world_offline_sim_cutoff_rounds_total` | 离线因预算被截断的轮数 | 偶发可；持续>0 说明容量不足 |
| `world_offline_sim_evicted_total` | LRU 转冷次数 | >0 需关注 |
| `world_offline_push_suppressed_total` | 离线被抑制的推送帧数 | 正常 >0 |

## 7. 容量实测（本次探究新增，可复跑）

脚本：`ai-script/explore/bench-offline-tick.mjs`（使用 `game-core` dist，
驱动方式与 `tickSession` 一致：`clock.pause()` + `stepPaused(200ms, 2000)`）

```bash
cd /home/nbb/projects/idle-dark-forever && node ai-script/explore/bench-offline-tick.mjs
BENCH_MAP=world.1 BENCH_ROUNDS=100 node bench-offline-tick.mjs
```

实测（本机，Node v24，稳态含刷怪与战斗）：

| 地图 | 稳态单位数 | µs / 角色 / tick | 2000 角色一轮 | 占 40ms 轮预算 |
|---|---|---|---|---|
| `world.1` | 5.0 | 3.2–3.5 | 6.96 ms | 17.4% |
| `world.9` | 5.0 | 2.65 | 5.30 ms | 13.3% |
| `world.13` | 5.2 | 2.56–2.70 | 5.12 ms | 12.8% |
| `chaos.t16` | 5.0 | 2.67–2.81 | 5.62 ms | 14.0% |

**推论**：
- 2000 个离线常驻角色约吃 **13%–17%** 的轮预算、约 **3%** 的墙钟；把
  `residentHotMax` 定在 5000 左右、`offlineSimBudgetMs=20` 是安全的。
- 内存沿用 `ai-docs/06 §1.3` 的 ~33KB/会话：5000 常驻 ≈ 165MB，可接受；上限存在的意义是
  防"离线人口 ≫ 在线人口"的无界增长，而不是当前就不够用。
- 与 `ai-docs/06` 旧基准（0.3–2.5µs/角色/tick）同量级；差异来自地图与单位数。

### 7.1 关键正确性验证：只推时钟就真的会战斗、涨收益

脚本：`ai-script/explore/check-gains.mjs`（**完全不走** `WorldService`/`isOnline`，
只有 `clock.pause()` + `stepPaused`，等价"离线期间世界仍在跑"）。

用 1 级有武器角色跑 `world.1` 10 虚拟分钟，实测：

```json

 "after":{"level":3,"exp":57.7,"gold":19},
 "expEvents":44,"deathEvents":44,"deathCamps":{"enemy":44},
 "lootEvents":25,"playerDealt":1972}
```

⇒ **44 次击杀、升到 3 级、掉 25 件**，全部来自"时钟推进"本身。
这证明 P0 的核心动作（`tickSession` 不再因离线早退）确实能产出用户要的"离线实时战斗"，

> 复跑坑（已踩）：最小复现里 `Player.fromJSON` 必须**不要**预置 `careers`，否则

> 伤害恒 0（表现为"模拟跑满却不掉血不击杀"）。这属于测试脚手架问题，不是内核缺陷；
